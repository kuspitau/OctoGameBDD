## Scope

P4-T04 adds explicit canonical relations for **how an existing canonical recipe is learned** without
changing recipe identity:

```text
recipe -> teaching item
recipe -> trainer creature
recipe -> quest reward spell
```

It deliberately does not copy derived availability such as:

```text
recipe -> vendor
recipe -> loot source
recipe -> zone
```

When a teaching item is sold, looted, rewarded by a quest or otherwise acquired, those paths remain
derivable through the existing P2/P3 item relations and P1 geography under D-008/D-019.

### Trainer semantics

`src/game/Handlers/NPCHandler.cpp` shows that a trainer exposes both:

```text
unit->GetTrainerSpells()
unit->GetTrainerTemplateSpells()
```

and that buying a trainer entry casts the `npc_trainer` / `npc_trainer_template` `spell` wrapper on
the player. The same code resolves that wrapper's `EffectTriggerSpell[0]` for trainer-state checks.
Trainer-template membership is attached to an actual creature through:

```text
creature_template.trainer_id
```

Therefore P4-T04 expands `npc_trainer_template` rows to the creature entries whose
`creature_template.trainer_id` selects that template. It retains the template ID as provenance and a
canonical column; it does not model an abstract trainer-template ID as a geographic acquisition
endpoint.

Trainer `spellcost`, `reqskill`, `reqskillvalue` and `reqlevel` are retained independently from the
recipe's own `SkillLineAbility.req_skill_value` requirement.

### Quest reward spell semantics

`Player::RewardQuest` establishes the exact wrapper selection rule:

```text
RewSpellCast when nonzero, otherwise RewSpell
```

The server then casts that wrapper spell. The reward path scans every spell effect slot when handling
`SPELL_EFFECT_LEARN_SPELL`; `LearnQuestRewardedSpells` likewise checks all effect slots. P4-T04
therefore does **not** impose a slot-0-only recipe-learning rule on quest reward spells.

### Server `spell_learn_spell` semantics and D-035

P4-T04 research found that D-034's original wording was too narrow when it said that only a DBC
`LEARN_SPELL` effect may prove wrapper -> learned-spell resolution.

`SpellMgr::LoadSpellLearnSpells()` loads:

```text
spell_learn_spell(entry, SpellID, Active)
```

into the same dependent-learning map used for DBC learn-spell dependencies. `Player` then learns
non-auto-learned dependent spells from that map when the parent spell is learned. The core also
explicitly detects database rows that duplicate a DBC `LEARN_SPELL` edge.

D-035 therefore refines D-034 for P4 acquisition resolution:

1. exact matching Octo `Spell.dbc` `LEARN_SPELL` evidence has priority;
2. if no matching Octo DBC edge exists, the pinned Tortoise `spell_learn_spell` row may prove the
   learning edge as lower-authority Turtle-lineage fallback evidence;
3. if both prove the same pair, the canonical relation keeps the Octo DBC proof kind and retains the
   server row as corroborating provenance;
4. a Tortoise fallback is never relabelled as exact Octo production truth;
5. names or coincident IDs never create a learning relation.

Recipe identity itself remains unchanged and continues to follow D-034.

## Migration 13

Migration:

```text
src/octogamedb/db/migrations/0013_recipe_acquisition_sources.sql
```

adds:

```text
recipe_teaching_items
recipe_trainer_sources
recipe_quest_learning_sources
```

Each materialized acquisition relation retains the acquisition wrapper spell and an explicit
`learning_proof_kind`:

```text
octo_dbc_learn_spell
tortoise_spell_learn_spell
```

For DBC proof, `learn_effect_index` preserves the selected source slot. All matching DBC effect slots
remain in provenance. For server fallback, `learn_effect_index` is null and `server_learn_active`
preserves the server row's `Active` value. When a server row corroborates a DBC edge its `Active`
value is retained while the DBC remains the selected proof kind.

Native teaching-item, trainer-creature and quest IDs are always retained. Their canonical foreign key
is nullable when that identity is not yet materialized; P4-T04 reports unresolved IDs instead of
fabricating placeholders.

## Source acquisition/revision contract

Existing ignored local configuration is reused:

```toml
[source_paths]
octo_dbc = "..."
tortoise_repo = "..."
```

No new path key and no `get_path.bat` are required. P4-T04 Level-2 evidence must be read from the exact
pinned Tortoise commit:

```text

```

The Tortoise acquisition revision is a deterministic manifest hash over the bounded base files plus
ordered `sql/database_updates/world/*_world.sql`, together with the checkout Git revision. A real Git
checkout supplied directly to the importer must also be clean for those inputs. The Level-2 BAT uses a
temporary clean clone at the pinned commit, so local edits in the configured checkout are logged but
never consumed as validation evidence. Relevant SQL mutations that the bounded replay cannot interpret
fail closed.

The Octo DBC revision uses the same deterministic three-file revision contract as P4-T02/P4-T03 and
must equal the latest successful `octo-dbc-recipes/4` identity import.

Cross-revision destructive absence reconciliation is deliberately not implemented in P4-T04.

It then stopped before any canonical mutation because the bounded Tortoise SQL replay encountered real
world-update syntax that the first parser revision did not yet support. The observed relevant forms
included:

- `npc_trainer` range predicates such as ``reqlevel > 6``;
- `quest_template` integer columns serialized as integral decimal literals such as
  ``RewSpellCast = 0.0``;
- composite tuple membership such as
  ``(entry, SpellID) IN ((46050,33427), ...)`` on `spell_learn_spell`;
- large `item_template` updates mixing relevant `spellid_N` assignments with quoted text fields;
- many `creature_template` / quest / item updates that referenced a bounded table but changed only
  unrelated fields and therefore should not require evaluating an unrelated WHERE expression.

The fail-closed behavior was correct; the parser contract was too narrow. No real canonical promotion
was performed and the migration-12 canonical/rollback hashes remained protected.

A second source-integrity finding was also material: a correct `git rev-parse HEAD` alone does not prove
that the configured Tortoise SQL bytes equal the pinned commit. At least one path reported by the local
replay (`20260505222630_world.sql`) is empty in the pinned GitHub commit, demonstrating that a working
tree can carry local SQL differences while still reporting the expected HEAD. P4-T04 therefore now
requires an exact clean SQL input tree for direct importer use.

### Parser/source correction after the first Level-2 attempt

Importer version `recipe-acquisition-sources/2` keeps the bounded fail-closed model and adds only the
reviewed SQL semantics needed by the observed source:

- UPDATEs that cannot assign any P4-T04 selected field are ignored before their WHERE clause is parsed;
- relevant WHERE predicates support scalar `=`, `!=`, `<>`, `<`, `<=`, `>`, `>=`, scalar `IN`,
  `IS NULL` / `IS NOT NULL`, and correlated tuple `IN`;
- integral decimal literals with a zero fractional part are accepted for integer columns, while true
  fractional values still fail closed;
- inert keyless/zero-key INSERT rows with no P4-T04 payload may be skipped, while keyless rows carrying
  relevant acquisition data remain fatal;
- item-template partial-row creation remains restricted to explicit positive `entry = ...` /
  `entry IN (...)` evidence; range predicates never fabricate absent item identities;
- unsupported relevant expressions/schema mutations continue to stop the import.

The focused synthetic suite now contains 6 tests and passes in the coding environment. It covers the
new range predicate, `0.0`, tuple-IN delete, irrelevant-update short-circuit and inert zero-key row in
addition to the earlier acquisition semantics.

The importer itself verifies the pinned Git revision and relevant SQL worktree cleanliness when given
a real Git checkout. The continuation BAT goes further: it reads the configured local Tortoise repo,
records any local differences for diagnostics, then creates a **temporary clean local clone** and checks
out the pinned commit using only local Git objects. Level-2 validation therefore neither trusts nor
modifies the configured working tree.
