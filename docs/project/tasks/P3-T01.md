# P3-T01 — first quest identity/endpoints vertical slice

**Status:** READY

## Goal

Establish the first bounded quest-domain vertical slice on top of the validated P0/P1/P2 foundation.
Do not begin with full quest ingestion. The first implementation should prove a clean path from quest
identity to giver/finisher endpoints and existing world geography with provenance and idempotence.

## Required source inspection before schema decisions

The implementation conversation must inspect the actual pfQuest quest inputs and the relevant
upstream resolver/browser code before assigning semantics to quest fields.

At minimum determine from primary source:

- which file(s) contain quest records and localized quest names;
- how giver/start relations are represented;
- how finisher/end relations are represented;
- whether endpoints distinguish creature and game-object IDs explicitly or by field family;
- how missing/empty/multiple endpoint lists are represented;
- whether Turtle overlays affect the bounded quest fields and, if so, their load/patch semantics;
- which exact source files must participate in deterministic source revision hashing.

Do not infer semantics merely from numeric shape.

## Initial bounded canonical scope

Expected first-slice model, subject to primary-source confirmation:

- `quests` identity keyed by native quest ID;
- explicit quest-giver relation(s) to creature and/or game-object templates;
- explicit quest-finisher relation(s) to creature and/or game-object templates;
- provenance for quest identity/name and each endpoint relation;
- query path from quest -> endpoint template -> P1 spawn -> zone/map.

Reuse P1 creature/game-object identity and spawn tables. Do not store arbitrary `quest -> zone` truth
when geography can be derived from endpoint spawns.

Relation-only named endpoint templates may be considered only under the same non-fabrication
principle established in P2: preserve a supported identity without inventing spawns. Missing identity
must be handled explicitly rather than guessed.

## Deferred unless required by source coherence

Later P3 tasks should normally cover:

- prerequisites/follow-ups;
- objectives;
- required items;
- guaranteed and choice rewards;
- richer quest restrictions/conditions;
- Turtle effective-view reconciliation beyond the minimum needed for this first vertical slice;
- full-data scaling/generalized ingestion.

If primary-source inspection shows that one of these fields is inseparable from the endpoint model,
document the concrete reason before widening P3-T01.

## Acceptance direction

Level 1 should include small source-shaped fixtures and tests for at least:

- quest identity/name parsing;
- creature giver and finisher endpoints;
- game-object giver and finisher endpoints if supported by pfQuest;
- multiple endpoints if supported;
- missing endpoint identity behavior;
- provenance/selection preservation;
- same-revision idempotence;
- derived endpoint geography through existing P1 world relations;
- CLI/query surface sufficient to inspect at least one quest and its endpoints;
- FK integrity and migration upgrade coverage if a schema migration is required.

Level 2 should validate the bounded importer against the configured real source files, confirm a clean
foreign-key check, same-revision idempotence and at least one real located quest endpoint with
traceable provenance.

## Architecture guardrails

Preserve established project rules:

- native IDs;
- explicit canonical domain relations;
- template/spawn separation;
- raw/source evidence distinct from canonical selection;
- source conflicts rather than silent overwrite;
- derived geography rather than duplicated location truth;
- deterministic source revisions;
- idempotent imports.

If existing decisions are insufficient or conflict with real quest-source behavior, record a new
architecture decision rather than silently generalizing a P1/P2 rule.
