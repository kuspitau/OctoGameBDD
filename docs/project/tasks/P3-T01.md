# P3-T01 — first quest identity/endpoints vertical slice

**Status:** IMPLEMENTED_AWAITING_LOCAL_VALIDATION

## Goal

Establish the first bounded quest-domain vertical slice on top of the validated P0/P1/P2 foundation.
Do not begin with full quest ingestion. The first implementation should prove a clean path from quest
identity to giver/finisher endpoints and existing world geography with provenance and idempotence.

## Required source inspection before schema decisions

The implementation conversation must inspect the actual pfQuest quest inputs and the relevant
upstream resolver/browser code before assigning semantics to quest fields.

At minimum determine from primary source:

- which file(s) contain quest records and localized quest names;
- how giver/start relations are represented;
- how finisher/end relations are represented;
- whether endpoints distinguish creature and game-object IDs explicitly or by field family;
- how missing/empty/multiple endpoint lists are represented;
- whether Turtle overlays affect the bounded quest fields and, if so, their load/patch semantics;
- which exact source files must participate in deterministic source revision hashing.

Do not infer semantics merely from numeric shape.

## Initial bounded canonical scope

Expected first-slice model, subject to primary-source confirmation:

- `quests` identity keyed by native quest ID;
- explicit quest-giver relation(s) to creature and/or game-object templates;
- explicit quest-finisher relation(s) to creature and/or game-object templates;
- provenance for quest identity/name and each endpoint relation;
- query path from quest -> endpoint template -> P1 spawn -> zone/map.

Reuse P1 creature/game-object identity and spawn tables. Do not store arbitrary `quest -> zone` truth
when geography can be derived from endpoint spawns.

Relation-only named endpoint templates may be considered only under the same non-fabrication
principle established in P2: preserve a supported identity without inventing spawns. Missing identity
must be handled explicitly rather than guessed.

## Implemented source contract

Primary-source inspection at the already pinned pfQuest revision
`104f35678ca39ab1fb78b655f815cc7016f5e0c8` established:

```text
db/quests.lua
  pfDB["quests"]["data"][quest_id]

db/enUS/quests.lua
  pfDB["quests"]["enUS"][quest_id]["T"] = title

quest.start.U = creature giver IDs
quest.start.O = game-object giver IDs
quest.end.U   = creature finisher IDs
quest.end.O   = game-object finisher IDs
```

Endpoint values are source arrays and may contain multiple native IDs. Missing fields mean no endpoint
of that supported family. The source also supports other start families such as `start.I`; P3-T01 does
not reinterpret those as creature/game-object endpoints.

The bounded identity scan uses the union of numeric IDs present in quest data and enUS localization. A
locale-only row with a valid `T` is preserved as quest identity with no inferred endpoints; a row that
has no usable enUS `T` is skipped with an explicit `missing_enus_name_ids` warning.

pfQuest runtime localization lookup uses the active locale with enUS fallback and reads quest title
field `T`. The base deterministic P3-T01 revision therefore hashes exactly:

```text
db/quests.lua
db/enUS/quests.lua
```

The reviewed Turtle overlay includes quest data/localization patch inputs and follows the existing
Turtle top-entry patch model. This proves that Turtle can affect the bounded quest facts, but D-027 is
explicitly limited to P2. P3-T01 therefore imports base pfQuest only and defers a quest-specific
effective-view reconciliation policy rather than extending D-027 by analogy.

## Implemented canonical contract

Migration 7 adds:

```text
quests(quest_id, name)
quest_creature_endpoints(quest_id, endpoint_kind, creature_id)
quest_gameobject_endpoints(quest_id, endpoint_kind, gameobject_id)
```

`endpoint_kind` is constrained to `giver | finisher`. Endpoint tables reference existing P1 template
identities with foreign keys. They do not duplicate spawn/zone/map data.

Provenance uses:

```text
quest name
  subject_kind = quest
  fact_key = name

quest endpoint
  subject_kind = quest
  fact_key = endpoint
  fact_instance_key = <giver|finisher>:<creature|gameobject>:<native_id>
  target = creature/gameobject native ID
  attributes = {endpoint_kind: ...}
```

A pfQuest endpoint whose target is absent from canonical P1 identity is still recorded as source
relation evidence and reported under `unresolved_endpoints`, but no placeholder template, spawn or
geography is invented.

The read surface `quest_by_id()` returns canonical endpoints and derives their locations through P1
spawns, zones and maps. Direct spawn map identity takes precedence over zone-derived map context by
using the same `COALESCE(spawn.map_id, zone.map_id)` rule already established by P1.
