# P3-T05 — quest item requirements and rewards

**Status: READY_FOR_IMPLEMENTATION**

## Goal

Add the next bounded P3 fact family: quantity-bearing quest/item requirements and item rewards.

The task must preserve the semantic distinction between:

- an item that is merely present in the P3-T04 objective membership export;
- an item requirement for which the reviewed source carries an explicit quantity;
- a guaranteed item reward;
- an item reward selected from a choice set.

Do not infer missing quantities by joining unrelated source lists by position or ID coincidence.

## Preconditions

- P3-T01 through P3-T04 are `VALIDATED`.
- The expected cumulative local baseline is `data/generated/octogamedb.sqlite3`, validated through
  migration 9 / P3-T04.
- D-029 / `docs/project/CANONICAL_DB.md` governs canonical DB backup and evolution.
- Existing P2 item identities are reused; missing targets remain explicit unresolved evidence unless a
  reviewed source contract justifies a safe identity anchor.
- P3-T04 objective membership/provenance must remain semantically separate from quantity-bearing
  requirement/reward facts.

Before any canonical mutation, replace:

```text
data/generated/octogamedb_bak.sqlite3
```

with an exact copy of the current canonical DB. Prefer a disposable validation copy first.

## Required investigation

Resolve and document before implementation:

1. which source relation carries each quantity and whether `0`, missing or empty has special meaning;
2. whether required source/provided items are the same gameplay relation as ordinary required items or
   require a distinct subtype;
3. whether P3-T04 `obj.I` is a complete superset/subset/independent projection of quantity-bearing
   item requirements;
4. how guaranteed and choice rewards are represented and whether source ordering matters;
5. whether a choice reward set has a complete-set identity independent from individual reward members;
6. whether repeated item IDs can legally occur in one requirement/reward family and, if so, how they
   are keyed without losing source meaning;
7. how Turtle whole-entry replacement/deletion affects complete requirement/reward sets;
8. whether localized reward names/icons are needed for identity resolution or can be derived entirely
   through canonical item IDs;
9. how unresolved item IDs remain auditable without fabricating canonical item identities;
10. whether any reward money/XP/reputation/spell semantics are inseparable from the item reward
    structure; if not, keep them deferred.

If the source contract forces materially broader semantics, document the conflict and update the
relevant architecture/decision files rather than silently expanding this task.

## Expected canonical direction

Prefer explicit domain tables. A likely direction, subject to source inspection, is conceptually:

```text
Quest -> required Item + quantity + requirement subtype
Quest -> guaranteed reward Item + quantity
Quest -> choice reward set -> Item + quantity
```

A complete effective-view fact may be necessary for each source-complete family so Turtle replacement
can delete stale managed materialization safely. Primitive member evidence and complete-set membership
must remain separate provenance concepts, following the established P1/P2/P3 reconciliation pattern.

Do not collapse guaranteed and choice rewards into one undifferentiated `quest_rewards` table if that
would lose gameplay semantics.

## Query/read-model acceptance target

Extend quest/item query surfaces so representative data can answer:

- which items and quantities a quest explicitly requires;
- which item rewards are guaranteed;
- which item rewards are alternatives in a choice set;
- the source/revision/policy provenance of each selected relation;
- whether an item target is resolved or unresolved;
- how a quantity-bearing requirement relates to P3-T04 objective membership without pretending the
  two source representations are identical.

Item geography should continue to derive through actual item acquisition relations where useful; do
not duplicate arbitrary quest/reward zone columns.

## Provenance and reconciliation requirements

Follow the established task-specific complete-view model:

- preserve source-shaped complete requirement/reward evidence;
- keep primitive item/quantity evidence separate from set-membership evidence;
- allow the active Turtle view to supersede only task-managed/default selections;
- protect explicit/custom canonical selections;
- remove stale managed rows only when the selected complete effective set excludes them;
- never delete historical source observations because canonical materialization changes;
- keep unresolved item IDs explicit;
- require deterministic same-revision idempotence.

Do not reuse P3-T04 `quest_objective_set` as a generic quest-item set unless primary-source inspection
proves semantic identity; default assumption is that these are distinct fact families.

## Explicitly deferred

Unless source inspection proves an inseparable dependency, keep these outside P3-T05:

- reward money/XP/reputation/spells not required to preserve item-reward semantics;
- arbitrary localized quest/reward prose;
- broader event/repeatability/profession/skill restrictions;
- new item-stat ingestion;
- P6 scaling/performance work;
- UI.
