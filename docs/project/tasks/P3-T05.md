# P3-T05 — quest item requirements and rewards

**Status: BLOCKED_ON_SOURCE_CONTRACT**

## Goal

Add the next bounded P3 fact family: quantity-bearing quest/item requirements and item rewards.

The eventual implementation must preserve the semantic distinction between:

- an item that is merely present in the P3-T04 objective membership export;
- an item requirement for which a reviewed source carries an explicit quantity;
- any distinct required source/provided-item relation and quantity;
- a guaranteed item reward;
- an item reward selected from a choice set.

Do not infer missing quantities by joining unrelated source lists by position or ID coincidence.

## Preconditions

- P3-T01 through P3-T04 are `VALIDATED`.
- The cumulative local baseline is `data/generated/octogamedb.sqlite3`, validated through migration 9
  / P3-T04.
- D-029 / `docs/project/CANONICAL_DB.md` governs any later canonical DB mutation.
- P3-T04 objective membership/provenance remains semantically separate from quantity-bearing
  requirement/reward facts.
- D-031 now requires an explicit source contract before this task may resume implementation.

### pfQuest raw-to-export loss is explicit

The pinned `toolbox/extractor.lua` reads raw quest-template item IDs such as:

```text
ReqItemId1 .. ReqItemId4
ReqSourceId1 .. ReqSourceId4
```

but uses them only to build the common item objective membership set that is later serialized as:

```text
pfDB["quests"]["data"][quest_id]["obj"]["I"] = { item_id, ... }
```

That distributed representation therefore proves item membership, not requirement subtype or
quantity. The extractor does not serialize `ReqItemCount*` and does not serialize guaranteed/choice
item reward fields. The currently published extractor checked on 2026-08-25 still does not export
`ReqItemCount`.

`SrcItemId` is temporarily included by the extractor while scanning item-use relationships and is then
removed from the objective item set. It is not a substitute for quantity-bearing requirement evidence.

### `quests-itemreq` is not quantity evidence

`db/quests-itemreq.lua` supports item-use target/spell relationships already modeled by P3-T04. It
does not carry a quest-required quantity and must not be reinterpreted for P3-T05.

### Public Turtle quest patch does not restore the missing facts

At reviewed revision `5b8eeeeb4119be9d075087f0f0e08c187b35ad61`,
`db/quests-turtle.lua` is empty. The currently published file checked on 2026-08-25 is also empty.
No public Turtle quest patch representation was found that supplies the missing count/reward fields.

## Consequence

The originally expected pfQuest/Turtle implementation path is not valid for P3-T05. Implementing a
migration/importer now would produce writable tables without a source contract capable of populating
them faithfully, or would require inventing quantities/reward semantics from `obj.I`. Both outcomes
conflict with D-005, D-023 and this task's no-inference requirement.

P3-T05 is therefore blocked, not failed or abandoned. The intended canonical functionality remains
valid, but its source must first be established by P3-T05A.

## Blocking task

```text
docs/project/tasks/P3-T05A.md
```

P3-T05A must establish a reproducible source/revision contract for the required quantity/reward fact
families before this task returns to `READY_FOR_IMPLEMENTATION`.

Source investigation must follow `docs/project/DATA_SOURCES.md` priority. Octo-specific authoritative
sources such as OctoDB are the first candidate. A pinned VMaNGOS/CMaNGOS-style source may be used as a
Vanilla baseline/fallback only with an explicit field/relation policy; it must not be silently treated
as Octo truth.

## Canonical direction after unblocking

Subject to P3-T05A's source contract, prefer explicit domain tables conceptually equivalent to:

```text
Quest -> required Item + quantity + requirement subtype
Quest -> guaranteed reward Item + quantity
Quest -> choice reward set -> Item + quantity
```

Complete effective-view facts may be necessary for source-complete families so later source
replacement can delete stale managed materialization safely. Primitive member evidence and complete
set membership must remain separate provenance concepts, following the established P1/P2/P3
reconciliation pattern.

Guaranteed and choice rewards must not be collapsed if doing so loses gameplay semantics.

## Query/read-model acceptance target after unblocking

Extend quest/item query surfaces so representative data can answer:

- which items and quantities a quest explicitly requires;
- which requirement subtype each item belongs to when the source distinguishes them;
- which item rewards are guaranteed;
- which item rewards are alternatives in a choice set;
- source/revision/policy provenance of each selected relation;
- whether an item target is resolved or unresolved;
- how a quantity-bearing requirement relates to P3-T04 objective membership without pretending the
  two source representations are identical.

Item geography should continue to derive through actual item acquisition relations where useful; do
not duplicate arbitrary quest/reward zone columns.

## Reconciliation requirements after unblocking

Once a source contract exists:

- preserve source-shaped complete requirement/reward evidence where the source is complete;
- keep primitive item/quantity evidence separate from set-membership evidence;
- protect explicit/custom canonical selections;
- remove stale managed rows only when the selected complete effective set excludes them;
- never delete historical source observations because canonical materialization changes;
- keep unresolved item IDs explicit;
- require deterministic same-revision idempotence.

Do not reuse P3-T04 `quest_objective_set` as a generic quest-item set unless P3-T05A establishes actual
semantic identity. The default remains that these are distinct fact families.

## Tests required after unblocking

Use source-shaped fixtures covering at least:

- required item with explicit quantity;
- any distinct required source/provided-item subtype found in the selected source contract;
- multiple guaranteed rewards where supported;
- multiple choice rewards with quantities;
- same item ID in distinct semantic families;
- missing/zero/empty count behavior according to the reviewed source contract;
- absent vs explicit empty complete sets if semantically distinct;
- source replacement/deletion semantics where the selected source family has them;
- missing canonical item identity;
- protected/custom selection behavior;
- stale managed-member cleanup;
- deterministic source revision calculation;
- same-revision idempotence;
- migration/FK upgrade behavior;
- quest/item query provenance.

Include a regression test proving that P3-T05 does not assign a quantity to a P3-T04 objective merely
because the same item ID appears elsewhere in the source.

## Level-2/full-data validation after unblocking

The eventual validator must:

1. run the complete tracked pytest/Ruff/compileall quality gate;
2. copy the P3-T04 canonical DB to a disposable P3-T05 validation DB;
3. apply P3-T05 migration/import/reconciliation to that copy;
4. run the operation twice and require zero canonical changes on pass two;
5. run FK/integrity checks;
6. report counts for required-item, guaranteed-reward and choice-reward families;
7. report unresolved/duplicate/odd source diagnostics with samples rather than requiring warnings = 0;
8. validate representative real quests for each supported family, including quantities and selected
   provenance;
9. check at least one relationship between a quantity-bearing requirement and P3-T04 objective
   membership without assuming universal equivalence;
10. only after disposable success, replace the D-029 backup and deliberately evolve the canonical DB.

No P3-T05 database validation or canonical mutation is appropriate while this task is blocked.

## Explicitly deferred
