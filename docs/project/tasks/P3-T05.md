# P3-T05 — quest item requirements and rewards

**Status: BLOCKED_ON_P3-T05B**

## Goal

Add the next bounded P3 canonical fact family: quantity-bearing quest/item requirements and item
rewards.

The final implementation must preserve the semantic distinction between:

- an item that is merely present in the P3-T04 objective membership export;
- an ordinary item requirement with an explicit source quantity;
- an auxiliary `ReqSource` item/drop-control fact;
- a quest-start provided/source item (`SrcItem`) and its quantity where a reviewed source exposes it;
- a guaranteed item reward;
- an item reward selected from a choice set.

Do not infer missing quantities by joining unrelated source lists by position, item-ID coincidence or
a default count.

## Semantic families

Keep these source meanings separate:

- `ReqItem*`: item and amount required for quest completion;
- `SrcItem*`: item provided to the player for the quest and, where source-backed, its amount;
- `ReqSource*`: auxiliary source/drop-control item data, **not** a turn-in requirement quantity;
- `RewItem*`: guaranteed rewards;
- `RewChoiceItem*`: alternatives in a choice reward set.

Preserve native source slot/order in provenance. Repeated item IDs across slots/families are allowed
and must not be deduplicated before source evidence is recorded. Choice slot order is presentation
order only, not preference/ranking.

For ordinary requirement/reward slots, source item ID zero means absent where the source contract is a
complete fixed-slot row. Unexpected nonzero-ID/zero-count records remain anomaly evidence rather than
being silently defaulted. `ReqSourceCount = 0` is the explicit documented special case.

## Canonical direction

Prefer explicit domain tables conceptually equivalent to:

```text
Quest -> required Item + quantity
Quest -> auxiliary/source Item + raw source-count semantics
Quest -> provided Item + quantity when known
Quest -> guaranteed reward Item + quantity
Quest -> choice reward set -> Item + quantity
```

Do not force `ReqSourceCount` into a generic column whose name/constraints imply “amount required to
complete”. Guaranteed and choice rewards must not be collapsed if doing so loses gameplay semantics.

Primitive item/count observations and source-complete set evidence remain separate provenance
concepts. Do not reuse P3-T04 `quest_objective_set` as a generic quest-item set.

## Resolution/reconciliation requirements

- preserve source-shaped primitive facts before canonical normalization;
- preserve source slot/family/duplicate evidence;
- use complete-set replacement/deletion only when the selected source contract is demonstrably
  complete for that bounded family;
- never delete from Octo live/OctoDB absence alone;
- apply Tortoise and CMaNGOS only through D-033's explicit family policy;
- protect explicit/custom canonical selections;
- never delete historical source observations because canonical materialization changes;
- keep unresolved native item IDs explicit without fabricated item identities;
- require deterministic source revisions and same-revision idempotence;
- expose source/revision/policy provenance in query/audit surfaces.

## Query/read-model acceptance target

Representative quest/item queries must answer:

- which items and quantities a quest explicitly requires;
- which auxiliary/source items are associated with the quest and their raw source-count semantics;
- which source/provided item is known and whether its count is known or unresolved;
- which item rewards are guaranteed;
- which item rewards are alternatives in a choice set;
- source/revision/policy provenance and native source slot/order;
- whether each item target is resolved or unresolved;
- how a quantity-bearing requirement relates to P3-T04 objective membership without pretending the
  source representations are equivalent;
- where live Octo, OctoDB, Tortoise and CMaNGOS disagree for the bounded family.
