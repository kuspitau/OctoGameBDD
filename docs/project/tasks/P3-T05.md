# P3-T05 — quest item requirements and rewards

**Status: READY_FOR_IMPLEMENTATION**

## Goal

Add the next bounded P3 fact family: quantity-bearing quest/item requirements and item rewards.

The implementation must preserve the semantic distinction between:

- an item that is merely present in the P3-T04 objective membership export;
- an ordinary item requirement with an explicit source quantity;
- an auxiliary `ReqSource` item/drop-control fact;
- a quest-start provided item (`SrcItem`) and quantity;
- a guaranteed item reward;
- an item reward selected from a choice set.

Do not infer missing quantities by joining unrelated source lists by position or ID coincidence.

## Preconditions

- P3-T01 through P3-T04 are `VALIDATED`.
- P3-T05A is `VALIDATED` and D-032 defines the source/authority contract.
- The cumulative local baseline is `data/generated/octogamedb.sqlite3`, validated through migration 9

- D-029 / `docs/project/CANONICAL_DB.md` governs any later canonical DB mutation.
- P3-T04 objective membership/provenance remains semantically separate from quantity-bearing
  requirement/reward facts.

### Semantics that implementation must keep separate

- `ReqItem*`: item and amount required for quest completion.
- `SrcItem*`: item and amount provided to the player for the quest.
- `ReqSource*`: auxiliary source/drop-control item data. It is **not** a turn-in requirement quantity.
  A nonzero `ReqSourceId` with `ReqSourceCount = 0` is valid in current CMaNGOS ClassicDB and means
  normal core/item-stack drop behavior rather than “requires zero”.
- `RewItem*`: guaranteed rewards.
- `RewChoiceItem*`: alternatives in a choice reward set.

Preserve native source slot/order in provenance. Repeated item IDs across slots/families are allowed
and must not be deduplicated before source evidence is recorded. Choice slot order is presentation
order only, not a preference ranking.

For ordinary requirement/reward slots, item ID zero means absent. Unexpected nonzero-ID/zero-count
records remain anomaly evidence instead of being silently defaulted; `ReqSourceCount = 0` is the
explicit documented exception.

## Canonical direction

Prefer explicit domain tables conceptually equivalent to:

```text
Quest -> required Item + quantity
Quest -> auxiliary/source Item + source count semantics
Quest -> provided Item + quantity
Quest -> guaranteed reward Item + quantity
Quest -> choice reward set -> Item + quantity
```

Do not force `ReqSourceCount` into a generic quantity column whose name/constraints imply “amount
required to complete”. Preserve its distinct meaning in schema/provenance.

CMaNGOS fixed-slot families can support complete baseline set evidence and bounded managed cleanup
under their fallback policy. OctoDB page evidence remains partial and cannot independently authorize
stale-member cleanup. Primitive member evidence and complete-set membership remain separate provenance
concepts.

Guaranteed and choice rewards must not be collapsed if doing so loses gameplay semantics.

## Query/read-model acceptance target

Extend quest/item query surfaces so representative data can answer:

- which items and quantities a quest explicitly requires;
- which auxiliary/source items are associated with the quest and their raw source-count semantics;
- which item, if any, is provided to the player and in what amount;
- which item rewards are guaranteed;
- which item rewards are alternatives in a choice set;
- source/revision/policy provenance of each selected relation;
- source slot/order where meaningful for traceability;
- whether an item target is resolved or unresolved;
- how a quantity-bearing requirement relates to P3-T04 objective membership without pretending the
  two source representations are identical.

Item geography should continue to derive through actual item acquisition relations where useful; do
not duplicate arbitrary quest/reward zone columns.

## Reconciliation requirements

- preserve source-shaped complete requirement/reward evidence where the source contract is complete;
- keep primitive item/count evidence separate from set-membership evidence;
- treat OctoDB HTML as partial positive evidence and never delete solely from page absence;
- apply CMaNGOS only through the D-032 Vanilla fallback policy;
- protect explicit/custom canonical selections;
- remove stale managed rows only when a selected complete effective set legitimately excludes them;
- never delete historical source observations because canonical materialization changes;
- keep unresolved item IDs explicit without fabricated item identities;
- preserve duplicate/repeated native slots before canonical normalization;
- require deterministic same-revision idempotence.

Do not reuse P3-T04 `quest_objective_set` as a generic quest-item set. These remain distinct fact
families.

Include a regression test proving that P3-T05 does not assign a quantity to a P3-T04 objective merely
