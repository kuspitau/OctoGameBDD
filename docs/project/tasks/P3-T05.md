# P3-T05 — quest item requirements and rewards

**Status: VALIDATED**

## Goal

Add the next bounded P3 canonical fact family: quantity-bearing quest/item requirements and item
rewards.

The implementation preserves the semantic distinction between:

- an item merely present in P3-T04 objective membership;
- an ordinary item requirement with an explicit source quantity;
- an auxiliary `ReqSource` item/drop-control fact;
- a quest-start provided/source item (`SrcItem`) and its quantity where a reviewed source exposes it;
- a guaranteed item reward;
- an item reward selected from a choice set.

Missing quantities are never inferred by joining unrelated source lists by position, item-ID
coincidence or a default count.

## Semantic families

- `ReqItem*`: item and amount required for quest completion;
- `SrcItem*`: item provided to the player for the quest and, where source-backed, its amount;
- `ReqSource*`: auxiliary source/drop-control item data, **not** a turn-in requirement quantity;
- `RewItem*`: guaranteed rewards;
- `RewChoiceItem*`: alternatives in a choice reward set.

Native source slot/order is preserved in provenance. Repeated item IDs across slots/families are
allowed and are not deduplicated before source evidence is recorded. Choice slot order is presentation
order only, not preference/ranking.

For ordinary requirement/reward slots, item ID zero means absent where the source contract is a
complete fixed-slot row. Unexpected nonzero-ID/zero-count records remain anomaly evidence rather than
being silently defaulted. `ReqSourceCount = 0` is the explicit documented special case.

## Implemented canonical model

Migration `0010_quest_item_facts.sql` adds:

```text
quest_required_items(
    quest_id,
    item_id,
    quantity
)

quest_required_sources(
    quest_id,
    item_id,
    raw_source_count
)

quest_provided_items(
    quest_id,
    item_id,
    quantity NULL when count is not selected/known
)

quest_reward_items(
    quest_id,
    item_id,
    quantity
)

quest_choice_reward_sets(
    quest_id,
    choice_semantics = 'choose_one',
    selected_member_count
)

quest_choice_reward_items(
    quest_id,
    item_id,
    quantity
)
```

The separation is intentional. `ReqSourceCount` is not stored in a generic “required quantity” column,
and guaranteed rewards are not collapsed into choice rewards. Native quest/item IDs remain FK-backed
canonical identities when materialized; unresolved source IDs remain provenance/audit evidence.

Primitive item/count observations and source-complete set evidence are separate provenance concepts.
P3-T04 `quest_objective_set` is not reused as a generic quest-item set.

## Implemented reconciliation behavior

`src/octogamedb/importers/quest_item_facts.py` consumes normalized P3-T05B snapshots and:

- records source-shaped primitive evidence before canonical normalization;
- records complete fixed-slot set evidence only when the source contract actually proves completeness;
- records every source slot occurrence as its own primitive provenance observation before any
  canonical normalization, while complete-family membership remains a separate set observation;
- applies D-033 per fact family;
- retains equal-priority disagreement as ambiguity/conflict instead of silently selecting by order,
  and clears only an obsolete **managed** winner rather than leaving stale canonical materialization;
- preserves previously selected partial-positive live/OctoDB facts when a later partial snapshot omits
  them;
- lets a newer positive observation from the same source/family supersede the older managed one;
- uses complete Tortoise fallback sets for stale managed fallback replacement only;
- never lets live/OctoDB absence alone delete unseen canonical members;
- protects explicit/custom canonical selections;
- never deletes historical source observations because canonical materialization changes;
- keeps unresolved quest/item IDs explicit and does not fabricate identities to satisfy foreign keys;
- treats ordinary invalid/zero counts as anomaly evidence while accepting raw `ReqSourceCount = 0`;
- keeps provided item ID and provided item count as separate selections, so a selected ID can remain
  materialized with `quantity = NULL` when no source-backed count is available;
- reports deterministic import details including canonical change counts, protected rows, unresolved
  targets, anomalies, ambiguities and conflicts.

Snapshot revisions remain source-specific and deterministic: Tortoise includes the pinned revision plus
full projection content hash; live includes its semantic reference plus capture hash; reviewed CSV
sources retain their declared revisions.

## Query/read-model implementation

`src/octogamedb/quest_items.py` exposes `quest_item_facts_by_id()`. `quest_by_id()` now includes the same
result under `item_facts`.

The model answers:

- which items and quantities a quest explicitly requires;
- which auxiliary/source items are associated with it and their raw source-count semantics;
- which source/provided item is known and whether its count is known or unresolved;
- guaranteed item rewards;
- choose-one reward alternatives;
- selected source/revision/policy, source slots and the matching per-slot source observations;
- whether the item target is resolved or unresolved;
- P3-T04 item-objective membership alongside explicit P3-T05 requirements, with
  `equivalence_assumed = false` and explicit set differences;
- retained source conflicts/ambiguities for the bounded fact family.

## Implemented validator

- `tortoise-full` — build a complete P3-T05B Tortoise projection (`quest_ids=None`) after verifying
  the configured repository is at the pinned revision;
- `apply` — migrate/reconcile one or more normalized source snapshots into a selected DB;
- `apply --twice` — immediately repeat the same import and fail unless the second pass produces zero
  canonical inserts/updates/deletes;

  writing, and refuses canonical mutation without the explicit flag.

validated P3-T05B `configure-paths` workflow.
