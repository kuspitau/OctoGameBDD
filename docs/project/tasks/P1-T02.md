# P1-T02 — Octo DBC map/area hierarchy vertical slice

## Goal

Resolve the authoritative canonical map/area hierarchy that P1-T01 deliberately left nullable, using the user's actual Octo client `Map.dbc` and `AreaTable.dbc` as direct client evidence.

This remains a bounded vertical slice. It establishes map/zone identity and hierarchy, provenance-aware source selection, and derived map context for existing zone-percentage spawns without attempting coordinate conversion or broad DBC ingestion.

## Base

- branch: `main`
- base commit: `d4310762f1e00b2664cb6d39eadf3e9abd407c46`
- P1-T01 is treated as validated for routing because its implementation is present on GitHub `main`, the project's validated source of truth.

## Public format evidence

The classic DBC container/field contract was checked against the CMaNGOS Classic source at revision:

- repository: `https://github.com/cmangos/mangos-classic`
- revision: `9b682be617ac61c127c23aa60d7b4ffbc0ce37e6`

Relevant evidence at that revision:

- `src/shared/Database/DBCFileLoader.cpp` reads classic `WDBC` files as a 20-byte header (`WDBC`, record count, field count, record size, string-block size), followed by fixed-size records and the string block;
- `src/game/Server/DBCStructure.h` documents `Map.dbc` fields used here: map ID, instance/map type, localized map name, and linked area ID;
- the same file documents `AreaTable.dbc` fields used here: area ID, map/continent ID, parent area ID, exploration flag, flags, exploration level, localized area name, faction-group mask, and liquid-type override;
- `src/game/Server/DBCEnums.h` defines classic map types `0..3` as common/world, instance, raid, and battleground;
- `src/game/Server/DBCStores.cpp` uses `AreaTableEntry::zone == 0` for top-level areas and non-zero values as parent-area links.

These sources are format/semantic references only. The canonical P1-T02 data source is the user's actual Octo client DBC pair, not CMaNGOS data.

The tracked binary fixture is synthetic/test-owned and only reproduces the WDBC shape needed for deterministic parser tests. No extracted Octo client data is committed.

## Scope

### DBC parser and source revision

Add a dependency-free parser for exactly:

- `Map.dbc`;
- `AreaTable.dbc`.

It must:

- validate the `WDBC` container header and declared file size;
- accept extra fields while requiring the classic fields used by this task;
- decode localized string slots conservatively;
- preserve native numeric map/area IDs;
- reject duplicate IDs and broken map/parent references;
- compute a deterministic source revision from the exact two input files when no explicit revision is supplied.

### Canonical map/zone materialization

Use the existing migration-3 tables; no new migration is required.

Materialize:

- `maps.map_id`, `maps.name`, `maps.map_kind` from `Map.dbc`;
- `zones.zone_id`, `zones.name`, `zones.map_id`, `zones.parent_zone_id` from `AreaTable.dbc`.

Additional DBC-only fields needed for later work are retained as source observations rather than prematurely expanding the canonical schema.

### Field-specific source selection

For canonical map/area identity and hierarchy facts, direct Octo client `Map.dbc` / `AreaTable.dbc` evidence is authoritative over lower-authority fallback observations.

The importer must:

- record source observations and import-batch links using P0 provenance primitives;
- select the Octo DBC observation with an explicit policy/reason for the affected map/area facts;
- preserve all losing/competing observations;
- remain idempotent for the same source revision.

This is a field-specific policy, not a universal rule that every DBC field outranks every other source.

### Derived map context for existing spawns

A spawn with a directly sourced `spawn.map_id` keeps that direct value.

When a spawn has only `zone_id`, location queries may derive map context through:

```text
spawn.zone_id -> zones.map_id -> maps
```

This must not:

- write a copied map ID into the spawn row merely for convenience;
- relabel `zone_percent` coordinates as `world` coordinates;
- perform any coordinate conversion.

### Local path handoff

Full validation requires an extracted DBC directory containing both required files.

The handoff includes root-level `get_path.bat` inside `changes.zip` to resolve/update:

```toml
[source_paths]
octo_dbc = "..."
```

according to `docs/project/LOCAL_PATHS.md`.

## Non-goals

- no full DBC catalogue/import framework;
- no MPQ extraction implementation;
- no conversion from pfQuest zone-percentage coordinates to world coordinates;
- no canonicalization of pfQuest's source-specific coordinate-frame first value;
- no WDB ingestion;
- no pfQuest-octo precedence implementation yet;
- no full-world performance profiling;
- no new UI/CLI browsing surface;
- no commitment of real Octo DBC files.

## Acceptance criteria

- the synthetic WDBC fixture parses deterministically;
- invalid/non-WDBC input is rejected clearly;
- the exact DBC pair has a deterministic content-derived source revision;
- map/zone native IDs and parent/map links materialize in migration-3 tables;
- repeated import of unchanged files creates no duplicate canonical rows or stable source observations while preserving per-run import-batch links;
- Octo DBC map/area evidence can supersede a previously selected lower-authority observation without deleting that evidence;
- a zone-only `zone_percent` spawn can report its canonical map through the zone relation while remaining `coordinate_space = 'zone_percent'`;
- existing P0/P1-T01 behavior remains green in the full repository suite;
- local validation against the user's real `Map.dbc` / `AreaTable.dbc` succeeds before P1-T02 is considered validated.

### Anonymous AreaTable rows

Real Octo client validation established that `AreaTable.dbc` may contain an isolated row with all localized-name fields empty (observed area ID `3884`). Such a row is not assigned a synthetic canonical name. If it is unreferenced by accepted areas, it is skipped with a warning and listed in import details. If an accepted area references an unnamed skipped parent, the importer fails the hierarchy validation.
