## Primary-source result

Inspected pfQuest revision:

```text
104f35678ca39ab1fb78b655f815cc7016f5e0c8
```

`toolbox/extractor.lua` constructs `V` directly from vendor SQL rows:

```text
npc_vendor:
  SELECT entry, maxcount ...
  V[entry] = maxcount

npc_vendor_template + creature_template:
  SELECT creature_template.Entry, maxcount ...
  V[creature Entry] = maxcount
```

`browser.lua` iterates the relation as `unitID, sellcount`, labels the source `Sold by`, and appends
the non-zero value to the vendor name.

Therefore the bounded source contract is:

```text
pfDB["items"]["data"][item_id]["V"][vendor_creature_id] = source_maxcount
```

The numeric value is not a price or a drop chance. P2-T03 preserves it verbatim as `max_count`
provenance and deliberately does not promote an interpretation of zero/non-zero into a generalized
stock/restock policy.

The reviewed Turtle addon has an `items-turtle` table patched at top-entry replacement level. Broad
Turtle/Octo item-overlay composition remains explicitly deferred; this task continues to import the
same bounded pfQuest item view as P2-T01/P2-T02. Existing P1 Turtle world reconciliation remains
relevant for canonical vendor creature/spawn geography.

## Implemented canonical model

Migration 6 adds:

```text
vendor_items(
  vendor_creature_id -> creatures.creature_id,
  item_id             -> items.item_id,
  PRIMARY KEY (vendor_creature_id, item_id)
)
```

The canonical relation records only that the creature sells the item. Source-specific `maxcount`
remains in provenance:

```text
subject_kind      = item
subject_key       = item_id
fact_key          = vendor_source
fact_instance_key = creature:<vendor_creature_id>
target             = creature:<vendor_creature_id>
attributes          = {max_count: source_maxcount}
```

This follows the existing decisions to preserve native IDs/provenance and use explicit domain
relations while keeping geography derived.

## Import / identity policy

The P2 importer now:

- parses `V` values as non-negative integers;
- registers each vendor relationship independently from direct/reference loot;
- reuses an existing canonical P1 creature when available;
- if the vendor is absent from the P1 static materialization but has a pfQuest enUS unit name,
  materializes only the creature template identity as a relation-only source anchor;
- never invents a vendor spawn, zone or coordinates;
- fails closed when a vendor target has neither a canonical creature identity nor pfQuest enUS name;
- remains idempotent for the same source revision.

Direct `U`/`O` and reference `R` behavior is unchanged.

## Query behavior

`find_item_sources()` / `python -m octogamedb item-sources` now return vendor paths alongside loot:

```text
path_kind        = vendor
chance_percent   = null
reference_loot_id = null
vendor_max_count = <selected source maxcount>
relation_source  = selected vendor_source provenance
```

When the same creature/spawn is both a loot source and a vendor, one source/location row may contain
multiple acquisition paths. Vendor acquisition does not alter or mathematically combine loot chances.

Vendor geography remains derived from:

```text
Item -> vendor_items -> Creature -> CreatureSpawn -> Zone -> Map
```

An unlocated relation-only vendor remains visible with null location fields.
