## Goal

Add the first stable bounded consumer-facing exploration surface for creatures and game objects. The
surface should make template entities directly searchable and explain their known spawn geography and
important cross-domain roles without flattening templates, spawn instances or derived relations.

Representative questions:

```text
Where is this creature or game object known to spawn?
Which creatures/gameobjects with this name occur in this zone/map?
What known item-acquisition relations involve this entity?
Is this creature a known vendor or trainer, and what validated relations prove that role?
Which quests use this entity as giver, finisher or objective?
Which evidence is unresolved, unlocated or only partially covered?
```

This is a read-only consumer/composition task. It is not a new world import, spawn reconciliation,
source-priority campaign, route planner or graphical map implementation.

## Existing semantics to preserve

Read only the code/docs needed for the task, but preserve at minimum the validated contracts from:

- P1-T01..T04: map/zone identities, creature/gameobject templates, distinct spawn instances, source
  provenance and effective-view reconciliation;
- P2-T01..T04 and P7-T02: direct/reference loot, vendor relations and acquisition semantics;
- P3-T01..T05 and P7-T03: giver/finisher/objective roles and explicit unresolved relations;
- P4-T04/P7-T04: direct/template trainer semantics where creature roles are exposed;
- D-025/D-026 and later audit decisions: do not invent a global source merge/priority rule.

Template identity is not spawn identity. A creature/gameobject may have zero, one or many known spawn
instances; absence of a currently materialized spawn is not universal proof of absence from the world.

## Bounded query scope

The initial public library surface should support, where the validated schema makes the predicate
well-defined:

- entity kind: creature or gameobject;
- exact native/canonical entity ID;
- case-insensitive name substring;
- known zone ID and/or map ID derived from spawn evidence;
- deterministic sorting and bounded result limits;
- explicit `known_match`, `known_non_match`, `unknown` semantics when a requested predicate is not
  fully provable from the validated source family;
- detail output containing every known spawn instance independently, with source/provenance and
  zone/map coordinates already represented by P1;
- relevant known cross-domain roles/relations described below.

Do not add speculative template attributes merely because fields exist in upstream DBC schemas. Any
new scalar family discovered to be required but not yet canonically materialized must be routed as a
separate prerequisite task rather than silently inferred.

## Cross-domain composition

### Item acquisition / loot / vendor

Expose validated relations in which the entity participates as a direct loot source, gameobject loot
source or vendor creature. Preserve reference-loot semantics and per-path drop chance exactly as P2 /
P7-T02 define them. Do not aggregate independent probabilities. Vendor stock/count metadata remains
distinct from chance.

The entity view may compose existing item-acquisition projections; it must not persist a new universal
`entity -> obtainable items in zone` truth.

### Quest roles

Keep quest roles separate:

```text
giver
finisher
objective creature
objective gameobject
```

Do not let a giver relation satisfy a finisher/objective filter or vice versa. Preserve unresolved
native IDs and the P7-T03 distinction between semantic relation and derived geography.

### Trainer role

For creatures, expose validated P4 trainer relations when present, including direct vs
template-expanded provenance. Do not collapse a trainer-template relation into a fabricated direct
trainer fact. Recipe details themselves remain owned by P7-T04 and may be composed rather than copied.

## Geography and three-state semantics

Geography is role/source derived from spawn evidence. Never introduce a universal primary
`creature -> zone` or `gameobject -> zone` fact.

For geography filters:

- a known matching spawn proves `known_match`;
- a complete validated spawn set may prove `known_non_match` only where the underlying source contract
  explicitly supports that negative;
- otherwise lack of matching materialized geography remains `unknown`.

If multiple world sources disagree, expose the selected/effective provenance according to existing P1
contracts rather than inventing a new union/intersection rule.
