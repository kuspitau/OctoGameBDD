# P4-T03 — recipe reagents and quantities

**Status: VALIDATED**

## Goal

Implement the next bounded P4 slice on top of the validated P4-T02 recipe identities:

- preserve each native recipe reagent item ID;
- preserve its native Spell.dbc reagent slot/index;
- preserve the exact corresponding required quantity;
- link to canonical `items` when that native item identity is already present;
- retain unresolved native item IDs without fabricating item identities;
- retain provenance and protected custom canonical selections;
- keep trainer/vendor/item/quest recipe-learning sources out of this task.

P4-T03 does **not** change the D-034 recipe identity contract. A recipe remains a separate entity
anchored to its proven crafting spell ID; reagents are relations from that recipe/crafting spell, not
properties of a teaching item or trainer row.

## Established P4-T03 source contract

1. A reagent is a positive native item ID in `Spell.Reagent[slot]` for the already canonical crafting
   spell/recipe.
2. `Spell.ReagentCount[slot]` is the exact source quantity for that same slot.
3. All eight raw slots are scanned independently. P4-T03 does not stop at the first empty slot, because
   the pinned Tortoise engine walks the complete array and slot identity is provenance-bearing.
4. `Reagent <= 0` is not materialized as an item relation. Negative values, if encountered, are
   counted in import diagnostics rather than converted into fabricated item IDs.
5. A positive reagent ID with quantity `0` is preserved exactly and reported as an anomaly/warning;
   it is not silently dropped or changed to `1`.
6. Missing canonical item identity does not invalidate the relation. `native_item_id` remains exact and
   `item_id` remains nullable, following the P4-T02 output-target pattern.
7. P4-T03 may only extend the exact DBC revision used by the latest successful
   `octo-dbc-recipes/4` P4-T02 identity import. Mixing recipe identity from one DBC snapshot with
   reagents from another is rejected.
8. Cross-revision P4-T03 refresh/reconciliation is deliberately not implemented. Once one reagent
   revision has been successfully imported, a different revision is rejected until a later task
   defines complete-set/absence semantics for that refresh.
9. Foreign/custom canonical selection policies remain protected. The managed P4-T03 policy only
   replaces its own selection for a reagent slot.
10. Recipe-learning/acquisition sources remain out of scope.

These rules refine the source contract but do not supersede D-034 or another accepted architecture
decision.

## Schema

Migration 12 adds:

```text
recipe_reagents(
    recipe_id,
    reagent_index,
    native_item_id,
    item_id,
    required_quantity
)
```

Key properties:

- primary key `(recipe_id, reagent_index)`;
- `reagent_index` constrained to `0..7`;
- `native_item_id > 0` always preserved;
- `item_id` nullable FK to canonical `items` and, when non-null, equal to `native_item_id`;
- `required_quantity >= 0`;
- indexes on canonical and native item IDs.

No quantity aggregation or deduplication across slots is performed.

## Validation script and canonical safety

New script:

```text
python scripts/validate_p4_t03.py validate ...
python scripts/validate_p4_t03.py promote ...
```

P4-T03 reuses the existing safe configuration key:

```toml
[source_paths]
octo_dbc = "..."
```

No new `get_path.bat` is required because this path contract was already configured and validated by
P4-T02.

The normal validation path:

1. hashes the migration-11 canonical DB;
2. copies it to `data/generated/p4_t03_validation.sqlite3`;
3. requires schema version 11 on that copy;
4. applies migration 12 only on the copy;
5. imports the matching reagent slice twice;
6. proves canonical idempotence, FK integrity and SQLite integrity;
7. verifies the source canonical DB hash never changed.

The `promote` path consumes successful validation JSON, verifies the exact same canonical baseline and
DBC revision, creates/replaces the D-029 byte-identical backup, then applies migration 12 and the
reagent import. Any exception during canonical mutation restores the backup.
