# P6-T05 — Migration-14 item-template coverage expansion and incremental promotion

Status: `READY_FOR_IMPLEMENTATION`

## Context

P6-T04 completed the first real D-029 promotion of the P6 item-template/stat slice.

Accepted starting canonical baseline:

```text
migration = 14 / 0014_item_template_facts.sql
SHA-256 = d57e0c79ac44d4fa0436b8c25e854a1d2b579d72dea1c327b23e9fe0fc4d1a8b
```

Immediate rollback at task start:

```text
migration = 13
SHA-256 = 623e29d83abd20335506d2a23dcbd525331de4f1bc10d38fccd7aa550a7613d7
```

Only three current item templates were eligible at the final P6-T04 promotion:

```text
7886
15784
41278
```

That is enough to validate the schema/import/promotion semantics, but it is not enough real-data
coverage for the planned P7 arbitrary item-stat exploration.

There is also a concrete implementation transition to solve: the existing P6-T02/P6-T03 acquisition
validators were written around the old accepted migration-13 SHA/migration and cannot simply be reused
unchanged now that the accepted canonical is migration 14.

## Goal

Establish a reusable **migration-14-era bounded acquisition + incremental promotion workflow**, then use
it for one additional real-client tranche.

P6-T05 should increase validated current item-template/stat coverage without:

- reapplying migration 14;
- treating historical WDB contents as current;
- scanning arbitrary/native numeric IDs;
- weakening D-036/D-037 freshness/provenance rules;
- requiring exhaustive acquisition of every remaining candidate.

## Required design work

### 1. Remove obsolete migration-13 assumptions from active P6 acquisition tooling

Inspect all active P6-T02/P6-T03/P6-T04 helpers/validators for hard-coded assumptions such as:

```text
EXPECTED_MIGRATION = 13
EXPECTED_BASELINE_SHA256 = 623e29...
```

Do not merely replace duplicated constants ad hoc in several scripts if a small shared accepted-baseline
contract can remove drift safely.

The tooling must still fail closed on an unexpected canonical DB. It must not silently accept "whatever
database exists".

### 2. Preserve old evidence without treating it as current

Existing P6-T02 refresh reports and the P6-T03 ledger remain evidence artifacts.

However:

- an old `refresh_proven_direct_observation` is not automatically current;
- promotion still requires exact current WDB raw-record SHA match;
- missing/drifted current records remain excluded;
- historical evidence must not be rewritten to pretend it came from the new migration-14 tranche.

Prefer a new P6-T05 campaign/tranche state artifact rather than mutating the validated P6-T03 historical
ledger into a different campaign identity.

Suggested ignored durable path:

```text
data/generated/p6_t05_campaign.json
```

The exact state model may reuse P6-T03 primitives if their semantics remain valid.

### 3. Bounded current-session acquisition tranche

Reuse the validated real-client item-probe mechanism.

Candidate discovery must remain limited to known canonical item IDs. No arbitrary numeric brute force.

The implementation should support configurable bounded sessions while preserving the existing hard
per-session safety cap.

For Level-2 validation, obtain a meaningful but bounded new positive tranche. Target:

```text
at least 10 newly refresh_proven_direct_observation item IDs
```

with a bounded maximum of:

```text
100 newly attempted unique item IDs
```

for the task validation run.

If external server instability prevents that target, stop and report the measured result rather than
weakening freshness rules.

### 4. Incremental migration-14 promotion

Create a deterministic incremental promotion plan that:

- starts from the accepted migration-14 canonical baseline;
- does **not** apply migration 14 again;
- selects only current-hash-matching `refresh_proven_direct_observation` records;
- excludes records already canonically selected with the same effective current evidence as no-ops;
- preserves protected/manual/custom selections;
- retains competing observations/provenance;
- is idempotent;
- can be rehearsed completely on a dedicated copy before real mutation.

### 5. D-029 on the migration-14 baseline

Before any real incremental write:

1. verify the accepted migration-14 canonical migration and SHA;
2. reject sidecars/drift/concurrent writers;
3. replace `_bak` with an exact copy of the migration-14 pre-promotion canonical;
4. SHA-verify that backup;
5. acquire guarded write access using the Windows-safe protocol validated by P6-T04;
6. perform only the incremental import/reconciliation;
7. restore from backup on any required validation failure.

After a successful P6-T05 promotion, `_bak` must represent the immediately previous **migration-14**
canonical state, not the old migration-13 file.

## Required implementation properties

- native item IDs preserved;
- no cache-only canonical identity fabrication;
- raw/source provenance preserved;
- exact current raw-record proof required;
- `historical_cache_only` excluded from automatic selection;
- timeout/missing remains unknown;
- deterministic plan/source/evidence revisions;
- repeated acquisition-session import is evidence-idempotent;
- repeated canonical incremental import is row/selection-idempotent;
- migration remains exactly 14;
- no schema migration is required unless a concrete blocker is discovered and separately justified.

## Required validation

### Level 1

Run the full repository gates against the final implementation:

```text
pytest --basetemp=<external temp>
python -m ruff check src tests scripts
python -m compileall -q src tests scripts
```

Also include focused tests for:

- accepted migration-14 baseline handling;
- rejection of the old migration-13 baseline as the active canonical;
- new tranche state/replay behavior;
- exact current-hash eligibility;
- already-promoted record no-op behavior;
- incremental promotion without migration reapplication;
- Windows-safe D-029 backup protocol;
- rollback on post-backup failure.

### Level 2

Using the real configured client and canonical DB:

1. verify the exact P6-T04 starting SHA;
2. run bounded acquisition sessions;
3. establish the required positive tranche or report a bounded external-instability blocker;
4. build the deterministic incremental promotion plan;
5. shadow/rehearse the complete promotion on a dedicated copy;
6. confirm real canonical remains unchanged during rehearsal;
7. perform one guarded real incremental promotion;
8. verify `_bak` equals the exact pre-P6-T05 migration-14 canonical;
9. verify the real canonical remains migration 14;
10. verify newly eligible templates/stats and representative queries;
11. rerun the same import/reconciliation and prove zero effective changes;
12. require `PRAGMA foreign_key_check = []`;
13. require SQLite integrity `ok`;
14. record the new accepted real canonical SHA in project memory.

## Coverage report

The closeout must record at least:

```text
canonical item population
current matching WDB coverage
new tranche attempted unique IDs
new refresh_proven_direct_observation count
new unknown/retryable count
incremental eligible item count
new item_templates promoted
new item_stat_modifiers promoted
already-current/no-op item count
final canonical SHA
rollback SHA
```

Do not claim whole-population item-template coverage.

## Non-goals

P6-T05 does not need to:

- acquire all remaining 15k+ historical campaign candidates;
- rotate/delete the user's WDB as a normal workflow;
- query arbitrary native IDs;
- add weapon damage/speed/block if still outside the adopted slice;
- add item spell/effect/tooltip semantics;
- build P7 search/UI;
- introduce a universal source priority.

## Routing after validation

After P6-T05, use the measured real template/stat coverage to decide whether:

- coverage is sufficient to start a bounded P7-T01 query/exploration task; or
- another explicitly justified P6 acquisition tranche is needed.

Do not route to P7 merely because migration 14 exists; route based on measured consumer-usable coverage.
