# P4-T02 — canonical spell / skill-line / recipe identity slice

**Status: READY_FOR_IMPLEMENTATION**

## Goal

Implement the first canonical P4 schema/import slice using the P4-T01 / D-034 identity contract.
The task is intentionally limited to identities and the minimum relations needed to say which native
crafting spell represents a recipe, which profession/skill line it belongs to, and which item(s) it
creates.

## Preconditions

- P4-T01 is `VALIDATED`.
- D-034 governs recipe/spell/item/trainer distinctions.
- The cumulative local canonical DB remains migration 10 / P3-T05.
- Any canonical mutation must follow D-029 and `CANONICAL_DB.md`.

## Required source review

Use the source contract established in P4-T01. Prefer direct Octo client DBC for actual Octo spell,
skill-line and skill-line-ability rows when configured and structurally compatible. Use the pinned
Tortoise/CMaNGOS structures as parser/semantic references, not as silently relabeled Octo truth.

Before writing migration/import code, verify the exact field indexes/layouts for the configured
`Spell.dbc`, `SkillLine.dbc` and `SkillLineAbility.dbc` source revision and fail closed on an unsupported
shape.

## Bounded canonical scope

Design the minimal migration needed for:

- native spell identity and query name/rank metadata;
- native profession/skill-line identity and name where available;
- recipe identity anchored to a proven crafting spell native ID while remaining a separate entity;
- recipe -> profession/skill-line membership and required profession skill value;
- recipe -> crafted item output relation preserving spell effect slot/order;
- provenance/import-batch observations sufficient to audit each selected fact/relation.

Do not add broad acquisition sources, reagents, economics, profession progression, combat spell
modeling or UI in this task.

## Required behavior

- preserve all native IDs;
- do not merge spell ranks by name;
- require both a skill-line membership and `CREATE_ITEM` evidence before treating a spell as a recipe;
- preserve multiple `CREATE_ITEM` slots instead of forcing one output;
- do not manufacture a final fixed output quantity when the source quantity is calculated/variable;
- report missing canonical output-item identities rather than fabricating them;
- keep source completeness/revision explicit;
- make the import idempotent and protect unrelated/custom selections under existing provenance rules.

## Validation expectations

### Level 1

Add/extend reduced WDBC fixtures and tests for at least:

- two profession/skill-line identities;
- separate spell IDs/rank text;
- one recipe with multiple output slots;
- one non-crafting spell that must not become a recipe;
- unsupported DBC shape failing closed;
- deterministic source revision;
- fresh migration plus rerun/idempotence/integrity checks.

Run pytest, Ruff and compile checks.

### Level 2

If the configured Octo DBC directory is required, use the existing `[source_paths].octo_dbc` path
contract. On a disposable copy of `data/generated/octogamedb.sqlite3`:

- verify DBC revision/layout;
- import representative recipes from at least two professions;
- verify native spell/skill-line IDs and names against source rows;
- verify output effect slots and unresolved output-item reporting;
- rerun with zero duplicate/material change;
- run FK/integrity checks and the task-specific audit/read commands.

Only after those checks pass may D-029 be used for deliberate canonical evolution from migration 10.

## Completion condition

The task is complete when the first canonical spell/skill-line/recipe identity slice is migrated,
source-backed, idempotent, queryable and locally validated as required. Route the next task narrowly
toward recipe reagents or learning/acquisition sources based on the resulting schema rather than
combining both automatically.
