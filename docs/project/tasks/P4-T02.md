## Goal

Implement the first canonical P4 schema/import slice using the P4-T01 / D-034 identity contract.
The task is intentionally limited to identities and the minimum relations needed to say which native
crafting spell represents a recipe, which profession/skill line it belongs to, and which item(s) it
creates.

## Canonical schema — migration 11

Migration:

```text
src/octogamedb/db/migrations/0011_recipe_identity.sql
```

adds:

```text
spells
  spell_id PK              native Spell.Id
  name                     nullable when no localized DBC value exists
  rank_text                nullable; ranks remain separate spell rows

skill_lines
  skill_line_id PK         native SkillLine.id
  name                     nullable when no localized DBC value exists

recipes
  recipe_id PK
  crafting_spell_id UNIQUE FK -> spells.spell_id
  CHECK recipe_id = crafting_spell_id

recipe_skill_lines
  recipe_id FK -> recipes
  skill_line_ability_id    native SkillLineAbility.id
  skill_line_id FK -> skill_lines
  required_skill_value     SkillLineAbility.req_skill_value

recipe_outputs
  recipe_id FK -> recipes
  effect_index             preserved CREATE_ITEM effect slot
  native_item_id           exact EffectItemType target
  item_id nullable FK -> items
```

`recipe_outputs.native_item_id` always preserves the observed target. `item_id` is populated only
when that native item already has a canonical `items` identity. Missing targets therefore remain
queryable/auditable without fabricating placeholder items.

The schema intentionally has no canonical fixed output-quantity column in P4-T02. Raw
`EffectBasePoints` / `EffectDieSides` and `quantity_semantics = calculated_spell_effect` are retained
in provenance for each output relation, preserving D-034 without turning those fields into an
incorrect fixed quantity.

## Import behavior

`src/octogamedb/importers/octo_dbc_recipes.py`:

- imports all native spell identities plus available name/rank metadata from the exact `Spell.dbc`;
- imports all native skill-line identities plus available names from the exact `SkillLine.dbc`;
- derives a recipe only when the same native spell has at least one `SkillLineAbility` membership and
  at least one `CREATE_ITEM` effect;
- preserves every qualifying membership row using its native `SkillLineAbility.id` and
  `req_skill_value`;
- tolerates cross-file `SkillLineAbility -> SkillLine` orphans when they belong only to non-recipe
  spells, reports their exact native IDs as source anomalies, and never fabricates a `SkillLine` row;
- still fails closed before SQLite import if a recipe-qualified membership points to a missing
  `SkillLine` identity, because that relation cannot be canonically materialized without invention;
- preserves every `CREATE_ITEM` effect slot independently;
- records unresolved output item identities as warnings and nullable canonical item links;
- records source facts/relations through the existing provenance/import-batch layer;
- uses managed selection policy `octo-client-dbc-recipe-identity` but preserves a canonical
  selection carrying any other policy instead of silently overwriting it;
- records the exact three-file content revision as a deterministic SHA-256 and exposes exact DBC
  layout/completeness metadata in the import summary;
- does not perform destructive absence reconciliation across client revisions in this bounded task.
  Exact-file completeness is explicit, but deleting previously known identities requires a separate
  deliberate contract rather than silently treating a client revision as universal non-existence.

Source key remains the existing:

```text

```

Importer version:

```text

```

### Level-2 attempt 2026-08-26 — cross-file orphan discovery

After the 173/692 layout correction, the next real-Octo run again passed the non-destructive
preflight, Ruff and script compilation. Parsing then reached `SkillLineAbility.dbc` row `5644`, which
references `skill_line_id=763` even though that identity is absent from the same Octo

orphans remain fatal.

### D-029 canonical promotion — only after Level 2 passes

Do not promote before the disposable validation succeeds, `sample_recipes` and unresolved outputs are
reviewed, and `data/generated/p4_t02_validation.json` is retained. Close programs that may write the
canonical DB, then run:

```bat
python scripts\validate_p4_t02.py promote ^
  --validation-json data\generated\p4_t02_validation.json ^
  --canonical-db data\generated\octogamedb.sqlite3 ^
  --backup-db data\generated\octogamedb_bak.sqlite3 ^
  --json-out data\generated\p4_t02_canonical_promotion.json
```

The promotion command is deliberately guarded. Before mutation it requires:

- the current canonical DB SHA-256 to match the exact migration-10 baseline recorded by the
  disposable validation JSON;
- the configured DBC revision to match the exact revision validated there;
- schema version `10`;
- the exact reviewed DBC layouts.

It then replaces the D-029 `_bak` file with a byte-identical copy of the pre-mutation canonical DB,
applies migration 11, imports the validated DBC source twice, requires the second import to produce
zero canonical inserts/updates, and runs FK/integrity checks. If mutation or a final invariant fails,
the command restores the canonical DB from `_bak` before returning failure.
