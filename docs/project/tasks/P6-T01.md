# P6-T01 — Item template/stat source contract and bounded ingestion slice

Status: `READY_FOR_IMPLEMENTATION`

## Context

P0-P5 established provenance, canonical-selection discipline, validated world/item/quest/recipe
vertical slices, and the source-conflict audit layer. P5-T08 closes the current world-spawn comparison
thread without changing D-025/D-026.

The project can now resume broader ingestion. The highest-value missing capability for the intended
query layer is filterable item template/stat data. `PROJECT.md` explicitly requires item exploration
and filtering by quality, levels, type/subtype, slot, armor/damage/speed/durability, stats, effects and
requirements. P2 intentionally implemented identity/acquisition relations first and did not generalize
Turtle item stats into canonical truth.

## Goal

Establish an explicit, source-native and field-aware contract for item template/stat facts, then
implement a bounded representative ingestion slice that proves the model/import/provenance path before
any full-data expansion.

The task should answer:

> Which currently available sources expose each required item-template/stat field for Octo, what are
> their exact semantics/completeness boundaries, and how should those observations be represented and
> selected without inventing a universal source priority?

## Required source investigation

Before schema/import implementation, inspect the current primary sources rather than assuming Vanilla
or Turtle layouts are sufficient. At minimum consider where actually available/relevant:

- direct Octo client/server-observable item data;
- OctoDB item-detail evidence;
- pfQuest base item data;
- installed/public `pfquest-turtle` item overlay semantics;
- structured Vanilla/CMaNGOS/VMaNGOS-style baselines only where needed as lower-authority coverage.

For every adopted source, record exact revisions or content-hash identity according to the project's
existing source contract. If a public source format is involved, inspect primary source code/docs.

Do not infer field semantics merely from display labels or positional coincidence.

## Initial bounded fact family

P6-T01 should prioritize scalar/filterable template facts that are necessary for useful item search and
whose source semantics can be established cleanly. Candidate fields include:

- quality;
- item level;
- required level;
- item class / subclass;
- inventory/equipment slot;
- armor;
- block;
- weapon minimum/maximum damage and attack speed;
- durability;
- base primary/secondary stat modifiers;
- explicit requirement/restriction fields when source-backed;
- icon/display identity where the source contract is stable.

Do not force every candidate into one task. If effects/procs/use-spells or tooltip text require a
separate semantic model, route them to a later bounded task instead of flattening them into strings.

## Model requirements

Preserve the existing architecture:

- native item IDs remain stable identity;
- raw/staging/canonical/derived layers remain distinct;
- every field/relation is provenance-backed;
- competing observations are retained;
- canonical selection policy is field-aware and explicit;
- absence in a partial source is not negative evidence unless that source proves complete-set
  semantics for the field;
- no universal source priority is introduced.

If schema evolution is required, add a migration and update `DATA_MODEL.md`, `ARCHITECTURE.md`,
`DATA_SOURCES.md`, `DECISIONS.md` and canonical-DB documentation as appropriate.

## Bounded implementation slice

Do not begin with a full-world import. Build small source-shaped fixtures and a representative bounded
item set covering materially different shapes, for example:

- armor with multiple stats;
- one-handed/two-handed weapon damage/speed;
- shield/block/armor;
- item with level/skill/class/race restrictions if exposed;
- custom Octo/Turtle item where available;
- conflicting observations between at least two source families if available;
- missing/partial field cases.

The bounded slice must demonstrate:

- deterministic parsing;
- idempotent import;
- provenance;
- conflict preservation;
- field-level canonical selection;
- trace/audit output sufficient to explain every selected value.

## Query acceptance target

The first consumer-facing proof should support a small provenance-aware query over the bounded sample,
such as:

```text
required_level <= N
AND inventory_slot = chest
AND agility >= X
AND stamina >= Y
```

or an equivalent representative stat query supported by the established source fields.

The query result must remain traceable to source observations and selections.

## Level 1 validation

Run all feasible:

- parser/source-contract unit tests;
- schema/migration tests if applicable;
- bounded importer/idempotence tests;
- conflict/selection tests;
- trace/query tests;
- full existing pytest suite when the repository is available;
- Ruff and compileall.

## Level 2 validation

If implementation requires local Octo client files, live/cache observations, full addon trees or the
canonical generated DB, provide exact local commands and expected invariants. Generate a task-specific
`get_path.bat` only for paths that cannot already be safely discovered/configured.

If the task mutates/evolves the canonical DB, follow D-029/CANONICAL_DB exactly: backup before mutation,
validate on a copy where practical, and do not mark the canonical baseline advanced until the full
human validation passes.

## Non-goals

P6-T01 must not:

- reopen P5 spawn-set authority without a concrete item-query dependency;
- merge Turtle and `pfquest-octo` world spawn sets;
- build the polished UI;
- perform an unbounded/full-source scrape before the bounded contract works;
- flatten unknown item effects into guessed text semantics;
- hard-code user-machine paths;
- introduce a universal source-priority ordering.

## Routing after P6-T01

Use measured source coverage and model complexity to decide whether the next bounded task is:

- full item template/stat ingestion with the validated contract;
- item effects/spell/tooltips semantics;
- additional acquisition-source coverage;
- or another missing domain required by the query layer.

Do not preselect that route until P6-T01 evidence exists.
