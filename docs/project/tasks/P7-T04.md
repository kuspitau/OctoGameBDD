# P7-T04 — provenance-aware recipe/reagent/acquisition exploration

Status: `READY_FOR_IMPLEMENTATION`

Base branch: `main`

Routing prerequisite: the complete P7-T03 implementation and validated closeout must be committed and
pushed. A fresh implementation conversation must resolve the actual current `main` head before editing.

## Goal

Turn the already-validated P4 recipe domain into a stable bounded consumer-facing exploration layer by
composing it with the validated P7 item/quest query surfaces.

The task should make it practical to answer questions such as:

```text
Which recipes produce this item?
Which recipes belong to this profession/skill line and required skill range?
What exact reagents and quantities does this recipe require?
How can this recipe be learned: teaching item, trainer, or quest reward spell?
Where can the teaching item be acquired?
Where are the known trainer creatures located?
What quest teaches the recipe and what is known about that quest's geography/progression?
Which learning/reagent targets are unresolved or have unknown acquisition/geography?
```

This is a read-only composition task. It is not a new recipe ingestion campaign, craft-profit model or
ownership/inventory feature.

P4 migrations already establish:

- spell and skill-line identities/names;
- per-recipe skill-line membership and `required_skill_value`;

P4-T04 explicitly forbids copying derived availability into primary recipe facts. That rule remains

## Required scope

At minimum, design and test a stable read-only library/CLI layer that can:

- search recipes by native recipe/crafting spell ID and case-insensitive spell/name text;
- filter by known skill-line ID/name and known minimum/maximum recipe `required_skill_value`;
- filter by known output native/canonical item ID;
- expose all materialized output effect slots separately, retaining native IDs and resolution state;
- expose all reagent slots separately with exact validated `required_quantity`, native ID, item identity
  when materialized, resolution state and provenance already available from P4 evidence;
- positively filter recipes by known reagent item ID;
- expose learning paths separately by kind: `teaching_item`, `trainer`, `quest_reward_spell`;
- retain direct vs trainer-template-expanded source semantics and P4-T04 trainer requirements/cost;
- retain `learning_proof_kind`, acquisition spell ID and available proof provenance;
- retain unresolved teaching-item/trainer/quest native IDs and make incompleteness explicit;
- optionally compose a teaching item's known P7-T02 acquisition paths without turning them into primary
  recipe acquisition rows;
- compose known trainer creature geography through existing P1/P7 world semantics;
- compose a resolved quest-learning source with the P7-T03 quest detail/query surface;
- positively filter by known learning-source kind and, where correctly representable, known derived
  zone/map geography for teaching-item acquisition, trainer location or quest context;
- keep those geography roles distinct rather than defining one universal recipe zone;
- return deterministic bounded output and a JSON-friendly CLI representation.

The implementation may add a focused `recipe_search.py`/CLI and small read helpers if P4 lacks a
consumer read model. Avoid changing importer responsibilities merely to simplify the query surface.

## Composition semantics

### Teaching item

The primary P4 fact is:

```text
recipe -> teaching item
```

How that item is obtained remains a derived composition through P2/P7-T02. A vendor, creature drop,
gameobject drop or reference-loot path for the teaching item is not a new primary recipe learning row.
Per-path drop probability remains per-path; do not combine probabilities. Vendor metadata remains
vendor metadata, not drop chance.

### Trainer

The P4 primary fact is a recipe-learning trainer creature relation. Geography is derived from that
creature's validated spawns through P1. An unresolved trainer native ID remains an unresolved learning
source and must not disappear merely because no creature identity/spawn can be joined.

### Quest reward spell

The P4 primary fact is a quest reward spell that teaches the recipe. When `quest_id` resolves, P7-T03
may provide giver/finisher/objective geography and progression, but the recipe must not inherit a single
primary quest zone. If the quest native ID is unresolved, preserve it as unresolved learning evidence.

## Coverage / negative-evidence rule

P7-T04 is an exploration layer, not a new source authority layer.

Do not manufacture universal negative facts from missing joins, missing item-template coverage, absent
known acquisition paths or absent geography. In particular:

- unresolved output/reagent/teaching item IDs remain known native relations with unresolved identity;
- a teaching item with no known P7-T02 acquisition path does not prove it cannot be acquired;
- a trainer with no known spawn does not prove the recipe has no geographic trainer availability;
- a quest learning source with unlocated endpoints/objectives remains valid quest learning evidence;
- absent migration-14 item-template facts remain unknown under D-036/D-037;
- do not infer additional reagents, quantities, output counts or learning sources from names/ID
  coincidence/default values.

Use explicit `known_match` / `known_non_match` / `unknown` behavior where predicates depend on partial
derived coverage. Exact P4 rows with complete scalar values may prove known matches/non-matches only
within their validated family semantics.

## Constraints

- Read-only consumer task: no canonical DB mutation.
- No schema migration unless a concrete query requirement proves the current model insufficient; if
  so, stop and route a separate bounded schema task.
- No new source ingestion/acquisition campaign.
- No new global source-priority rule.
- Preserve protected selections/provenance and native IDs.
- Do not persist `recipe -> vendor`, `recipe -> loot source`, `recipe -> zone` or equivalent simplified
  primary relations.
- Do not collapse trainer, teaching-item and quest learning paths into one source kind.
- Do not combine drop probabilities or infer market/craft economics.
- Keep output deterministic and bounded.

## Validation expectations

### Level 1

Use tracked/source-shaped fixtures to cover at least:

- recipe ID/name and skill-line/required-skill filters;
- output item lookup and unresolved output identity;
- multi-reagent recipe with exact slot quantities;
- unresolved reagent identity retained;
- teaching-item learning source and its composed direct/reference/vendor acquisition paths where fixture
  coverage permits;
- direct trainer and template-expanded trainer learning sources;
- trainer requirements/cost retained;
- located and unlocated trainer geography;
- quest reward spell learning source composed with P7-T03 detail;
- unresolved quest learning source retained;
- learning proof kind/acquisition spell provenance;
- separation of teaching-item/trainer/quest geography roles;
- conservative unknown for missing derived acquisition/geography;
- deterministic ordering/limits;
- CLI/JSON output if a CLI surface is added.

### Level 2

Run read-only against the accepted canonical DB and automatically select representative real samples
for:

- a recipe with skill-line membership and resolved output;
- a recipe with multiple reagent slots/quantities;
- a teaching-item learning source;
- a teaching item with a known P7-T02 acquisition path when present;
- a direct trainer learning source with known geography;
- a template-expanded trainer learning source;
- a quest reward spell learning source;
- an unresolved teaching-item or trainer relation (known to exist in the validated P4-T04 baseline);
- deterministic repeat output;
- `PRAGMA foreign_key_check = []` and `PRAGMA integrity_check = ok`;
- byte-identical canonical SHA before and after.

Accepted baseline at task routing:

```text
schema_version=14
canonical_sha256=60aeb4093fa68e6b3a7a8c513e5a127862d88db8bc9aab4f6f3e4a0f4c0d5a23
```

Do not hard-code representative recipe/item/trainer/quest IDs in the task contract. The validator
should discover suitable real examples from the accepted canonical and report the observed IDs.

## Non-goals

P7-T04 does not implement:

- auction-house/live market prices, craft cost or profit calculations;
- owned-material counts, character inventory, bank or recipe-known state;
- recursive multi-stage bill-of-materials optimization beyond a bounded recipe/reagent inspection
  surface;
- generalized “best place to farm all reagents” route planning;
- new item-template field acquisition;
- saved searches, weighted scores or graphical UI;
- generalized dungeon/raid classification.

Those remain later bounded tasks. P7-T04 should establish a semantically safe recipe consumer surface
that later economics, ownership and UI features can compose without bypassing P4/P7 provenance rules.
