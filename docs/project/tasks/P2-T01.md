# P2-T01 — First item/acquisition vertical slice

## Status

`VALIDATED`

## Base

- GitHub branch: `main`
- base commit: `582810dfe6ae41e4eec9af303d6f98a772830ef8`

## Goal

Open P2 with the smallest useful item/acquisition slice that exercises the P0 provenance foundation
and the canonical P1 world model end to end.

The acceptance path is:

```text
pfQuest item
  -> canonical Item
  -> direct creature/game-object loot relation + chance
  -> canonical P1 source template
  -> canonical spawn
  -> zone/map context
```

The source/location result must be derivable and traceable without introducing `item -> zone` as
primary truth.

## Source contract

P2-T01 uses the public pfQuest structure already established as a project source. The inspected
upstream format at revision `104f35678ca39ab1fb78b655f815cc7016f5e0c8` exposes:

```text
db/items.lua
  pfDB["items"]["data"][item_id]["U"][creature_id] = chance_percent
  pfDB["items"]["data"][item_id]["O"][gameobject_id] = chance_percent
  pfDB["items"]["data"][item_id]["R"] = ...
  pfDB["items"]["data"][item_id]["V"] = ...

db/enUS/items.lua
  pfDB["items"]["enUS"][item_id] = item_name

db/enUS/units.lua
  pfDB["units"]["enUS"][creature_id] = creature_name

db/enUS/objects.lua
  pfDB["objects"]["enUS"][gameobject_id] = gameobject_name
```

Only `U` and `O` are materialized in this slice. `R` and `V` are counted and deferred.

The exact four local inputs used by this slice (`items.lua`, item names, unit names, object names)
are identified by a deterministic content-derived SHA-256 revision. This identifies the imported
bytes; it does not claim equivalence with an upstream commit.

## Canonical schema

Migration 4 adds:

```text
items
creature_loot
gameobject_loot
```

`items.item_id` preserves the native item ID.

Loot tables are explicit domain relations under D-007. Their primitive facts are:

```text
Creature C drops Item I with chance P
GameObject G drops Item I with chance P
```

No zone is stored on the loot relation. Obtainable geography is derived through P1 spawns under
D-008 and D-009.

## Provenance contract

Item names are scalar observations:

```text
subject_kind = item
subject_key  = item_id
fact_key     = name
```

Direct loot relations are relation observations:

```text
subject_kind      = item
subject_key       = item_id
fact_key          = loot_source
fact_instance_key = creature:<id> | gameobject:<id>
target.kind       = creature | gameobject
target.key        = source native ID
attributes        = {chance_percent: P}
```

The first observation is selected only when a relation/name has no prior canonical selection.
Competing later observations remain preserved and are not silently allowed to replace an existing
explicit selection.

## P1 dependency and relation-only source policy

A canonical `creature_loot`/`gameobject_loot` row requires a canonical source template because the
relation tables use foreign keys. P1 intentionally models template identity separately from spawn
instances, so lack of a static P1 spawn does not imply that the source entity is invalid.

Level-2 validation exposed exactly this case for pfQuest gameobjects `180523` (`Apple Bob`) and
`180671` (`Xandivious' Demon Bag`): they are named pfQuest gameobjects referenced by item loot but
are not materialized by the static P1 world slice.

P2-T01 therefore materializes a missing direct-loot target as a **relation-only template** when the
corresponding pfQuest enUS unit/object table supplies a real name. The name receives normal pfQuest
provenance. No spawn, zone, or coordinates are synthesized, and queries expose null geography.

If a target is absent both from canonical P1 and from the pfQuest enUS identity table, the import
still fails closed with exact IDs rather than creating an invented placeholder.

## Query contract

`find_item_sources(connection, item_id)` returns the canonical item plus direct source rows.

For each direct source it may expose:

- source kind/ID/name;
- chance percentage;
- canonical spawn identity and coordinates, when present;
- zone and map context, derived from existing P1 relations;
- selected provenance for the loot relation;
- selected provenance for the spawn position.

A source with no canonical spawn remains visible with null geographic fields.

The CLI surface is:

```text
python -m octogamedb import-pfquest-items <PFQUEST_ROOT> [--source-revision REV] [--db PATH] [--json]
python -m octogamedb item-sources <ITEM_ID> [--db PATH] [--json]
```

## Level 1 acceptance

Tracked fixture tests must cover:

- migration-4 discovery and upgrade behavior;
- source-shaped pfQuest item parsing;
- deterministic content revision identity;
- invalid chance rejection;
- item/direct-loot materialization;
- repeated same-revision idempotence;
- provenance reuse across repeated batches;
- derived spawn/zone/map lookup;
- relation/location source attribution;
- named relation-only target materialization without invented geography;
- fail-closed behavior when a target has no canonical or pfQuest enUS identity;
- CLI import/query behavior.

## Level 2 acceptance

Against the user's installed pfQuest/Turtle data:

1. create a fresh generated validation DB;
2. import the base P1 pfQuest world;
3. reconcile the active Turtle world view;
4. compute/import the real pfQuest item revision;
5. import the same item revision again;
6. query at least one located item;
7. run `PRAGMA foreign_key_check`.

Expected invariants:

- non-zero item and direct-loot coverage;
- zero canonical changes on the second identical item import;
- traceable relation provenance;
- traceable location provenance where P1 provides it;
- no foreign-key errors;
- deferred `R`/`V` counts may be non-zero.

## Explicitly deferred

- item stats/effects/requirements;
- reference-loot expansion;
- vendors;
- item/container and specialized loot;
- Turtle/Octo item overlay composition;
- cross-revision disappearance/complete-set semantics;
- full-data P6 scaling.
