# P6-T03 — Resumable direct-Octo acquisition campaign for known canonical cache misses

Status: `VALIDATED`

Validated: 2026-08-29

## Goal

Scale the validated five-ID P6-T02 freshness probe into a deterministic, resumable acquisition
campaign over known canonical item IDs absent from the current Octo item cache, without weakening
D-037 evidence semantics or mutating the canonical database.

## Retained decisions and boundaries

P6-T03 retains D-036/D-037 unchanged:

- candidate IDs come only from existing canonical item identity;
- no arbitrary numeric brute force;
- one outstanding client query at a time;
- bounded client/session retries;
- timeout/missing is unknown, never negative item evidence;
- current freshness requires pre-session cache miss + successful current-session load + post-session
  raw WDB record;
- pre-existing cache evidence remains positive but historical;
- canonical DB remains read-only at migration 13;
- migration 14 is not promoted during this task.

## Delivered implementation

Primary surfaces:

```text
src/octogamedb/itemcache_campaign.py
scripts/validate_p6_t03.py
scripts/validate_p6_t03_resume.py
validate_P6_T03_full_local.bat
tests/test_itemcache_campaign.py
tests/test_p6_t03_validator.py
tests/test_p6_t03_resume.py
```

The campaign adds:

- ignored durable ledger at `data/generated/p6_t03_campaign.json`;
- atomic `fsync` + `os.replace` checkpoints;
- deterministic candidate/campaign/request/merge revisions;
- default batch size 10, hard maximum 20;
- campaign attempt cap of two client sessions per item ID;
- operational states for queued/in-flight/fresh/historical/unknown/deferred evidence;
- deterministic spread selection with a retry slot when retryable unknowns exist;
- pre-session historical-cache reconciliation;
- conservative partial/missing SavedVariables recovery;
- duplicate/no-op completed-session replay detection;
- campaign metrics/reporting and canonical SHA before/after checks;
- resume-aware BAT orchestration that preserves an existing durable `in_flight` batch rather than
  reserving a replacement batch after a CMD restart.

### Interruption/DDoS session

The first real campaign session was affected by server DDoS/disconnections. Its final classification
was deliberately conservative:

```text
attempted unique IDs           = 10
refresh_proven                 = 0
unknown_retryable              = 10
newly materialized WDB records = 6
canonical DB unchanged         = true
```

The CMD had been closed after preflight. The durable ledger retained the exact `in_flight` batch.
After the client command eventually completed, manual `postvalidate` merged the existing session and
an immediate second `postvalidate` returned the same merge revision with `duplicate_noop=true`.

This incident therefore proved persistence, interruption survival, conservative classification,
idempotence and canonical read-only behavior even though it did not prove positive acquisition.

## Acceptance result

P6-T03 is `VALIDATED` because all blocking acceptance criteria are satisfied:

- the complete repository test suite passes;
- Ruff and compileall pass;
- campaign selection is bounded and canonical-ID-only;
- durable state survives an actual interrupted CMD workflow;
- completed-session replay is a duplicate/no-op;
- a stable automatically selected multi-ID session produced eight
  `refresh_proven_direct_observation` results;
- unknowns remain unknown;
- historical cache evidence is not promoted to fresh evidence;
- the canonical migration-13 DB remained byte-identical throughout.

Accepted non-blocking residual risk:

- the post-hotfix wrapper's dedicated automatic `in_flight` restart branch was not deliberately
  replayed end-to-end after the wrapper was added;
- focused tests cover that branch, and the underlying real interrupted-ledger + completed-capture
  recovery behavior was already exercised successfully in the actual DDoS interruption;
- no further manual replay is required to close P6-T03.

## What P6-T03 does not prove

P6-T03 does not claim:

- whole-item-population direct queryability;
- that current cache coverage is complete;
- that timeout/missing means an item is absent;
- that historical cache records are current;
- that migration 14 is ready merely because acquisition works;
- that the canonical DB has advanced beyond migration 13.

The campaign remains useful as an ongoing bounded acquisition mechanism, but continuing thousands of
manual batches is not a prerequisite for the next project task.

## Routing

P6-T03 routes to **P6-T04 — bounded migration-14 canonical promotion of validated item-template/stat
evidence**.

P6-T04 is a separate D-029 canonical mutation task. It must decide and validate exactly which P6
