# P6-T03 — Resumable direct-Octo acquisition campaign for known canonical cache misses

Status: `READY_FOR_IMPLEMENTATION`

## Context

P6-T02 validated D-037's direct item-query freshness mechanism on the user's real Octo client:

```text
canonical item identities                 = 23336
cache records matching canonical identity =  6667
canonical IDs missing from cache          = 16669
bounded missing-ID probe                  =     5
refresh-proven direct observations        =     3
unknown outcomes                          =     2
```

A known canonical ID absent from the pre-probe cache can therefore be queried with strong currentness
proof when the current-session load produces a post-session raw WDB record. P6-T02 intentionally
proved mechanism, not scalable acquisition.

P6-T03 should scale that exact mechanism conservatively enough to become a practical source-acquisition
workflow while preserving all D-037 evidence boundaries.

## Goal

Build a reproducible, resumable acquisition campaign over **known canonical item IDs that are absent
from the current cache**.

The workflow should answer:

> Can OctoGameBDD maintain a durable queue/checkpoint, acquire bounded batches across one or more real
> client sessions, resume without losing or duplicating evidence, and quantify success/timeout behavior
> well enough to decide whether direct acquisition can support broader P6 ingestion?

P6-T03 remains a source acquisition/measurement task. It is not yet a migration-14 promotion task.

## Starting implementation to reuse

Do not rebuild the P6-T02 mechanism from scratch. Inspect and extend the validated implementation,
including at minimum:

```text
src/octogamedb/itemcache_coverage.py
scripts/validate_p6_t02.py
scripts/octogamedb_item_probe/
tests/test_itemcache_coverage.py
tests/test_p6_t02_validator.py
```

Preserve the validated parser and D-037 classification behavior unless new runtime evidence requires a
recorded decision change.

## Candidate universe

Campaign candidates must originate from canonical `items.item_id` only.

The initial candidate set is the deterministic difference:

```text
canonical item IDs - IDs present in the campaign preflight itemcache snapshot
```

Rules:

- no arbitrary numeric range scanning;
- no guessed native IDs;
- cache-only native IDs are not automatically added to canonical identity or to the campaign queue;
- already refresh-proven IDs should not be queried again merely to increase counters;
- terminal unknown/timeouts may be retried only under an explicit bounded retry policy;
- candidate ordering/revision must be deterministic and auditable.

## Durable acquisition ledger

Introduce an ignored local campaign/checkpoint artifact, not a canonical DB table.

A suitable location is under:

```text
data/generated/
```

The exact format is an implementation choice, but it must be deterministic and machine-readable. JSON
or a dedicated disposable SQLite ledger are both acceptable if tests prove crash-safe/idempotent
behavior.

Per campaign, retain enough information to reconstruct why every ID is in its current state:

- campaign format/version;
- canonical DB SHA and migration baseline used to form the candidate universe;
- initial coverage revision/cache snapshot identity;
- ordered candidate IDs or deterministic candidate-set revision;
- per-ID state;
- attempt/session count;
- last probe status;
- freshness class;
- pre-record hash when applicable;
- post-record hash when available;
- client/locale/realm/session metadata where exported;
- timestamps as metadata, never as source revision;
- terminal/retryable classification;
- reason for unknown/failure.

The ledger must be safe to reopen after interruption. Re-running the same completed session import must
not duplicate or downgrade evidence.

## Per-ID campaign states

Reuse D-037 evidence classes and add only operational queue states where needed.

At minimum distinguish:

```text
queued
in_flight
refresh_proven_direct_observation
session_observed_freshness_limited
historical_cache_only
unknown_retryable
unknown_terminal_or_deferred
```

Do not silently convert an interrupted `in_flight` row to success or absence. Recovery must reconcile
it against actual SavedVariables/WDB evidence or return it to an explicit retryable state.

## Client/session behavior

The real-client path must preserve the validated safety property:

```text
one outstanding item query at a time
```

P6-T02 validated:

```text
poll interval       = 0.20 s
retry interval      = 3.0 s
timeout per ID      = 15.0 s
maximum attempts    = 5
```

Do not make these more aggressive without new evidence. P6-T03 may improve orchestration around them.

The current P6-T02 probe accepts at most 20 explicit IDs. P6-T03 may either preserve this as the
session batch bound or justify a different bounded session queue through explicit testing. A larger
campaign ledger does **not** require flooding the client: it can feed bounded sessions from a much
larger deterministic candidate population.

## Minimize human work

The workflow should avoid requiring the user to hand-pick/copy large ID lists.

Preferred direction:

1. desktop preflight computes the next deterministic bounded batch from the campaign ledger;
2. it stages the addon/session input while WoW is closed or prints/copies one exact short command;
3. the addon processes the batch asynchronously, one ID at a time;
4. the user logs out/exits so WDB/SavedVariables flush;
5. desktop post-processing imports the session result into the campaign ledger;
6. a later invocation resumes with the next eligible batch.

If safe staging of the queue into addon data/SavedVariables is implemented, it must be source-shaped,
atomic while the client is closed, and covered by tests. Do not corrupt unrelated WoW SavedVariables.

## Cache handling

Do not delete or rotate the user's WDB merely to force historical items fresh in P6-T03.

This task is specifically routed around **currently cache-missing canonical IDs**, for which P6-T02
already proved the freshness mechanism.

A later task may investigate controlled cache rotation/backups if refreshing historical-cache-only
records becomes necessary, but that requires its own safety and provenance contract.

## Coverage/campaign reporting

Each checkpoint and final report should include:

- initial canonical population;
- initial matching cache coverage;
- campaign candidate count;
- attempted unique IDs;
- refresh-proven count/rate;
- session-limited count/rate;
- unknown/timeout count/rate;
- retries and terminal/deferred counts;
- newly materialized WDB record count;
- duplicate/no-op session imports;
- remaining unattempted candidate count;
- remaining canonical cache-missing count after the session/campaign;
- representative success/unknown IDs across low/high/custom ranges;
- canonical DB SHA before/after.

Do not label the remaining population as unavailable on Octo.

## Source revision/provenance

Campaign identity must not depend only on timestamps or a mutable WDB path.

Use deterministic hashes/revisions over the relevant bounded inputs, including where appropriate:

- canonical item-ID population and canonical DB SHA;
- campaign candidate-set revision;
- pre/post WDB header/membership/raw-record hashes;
- exact per-session requested ID list;
- machine-readable addon export content.

Raw/local campaign artifacts remain ignored under D-014.

Accepted baseline remains:

## Level-1 validation

Add focused deterministic tests for at least:

- candidate-set construction from canonical/cache membership;
- deterministic batch selection;
- ledger creation/version/revision;
- successful session merge;
- idempotent repeated merge of the same session;
- resume after partial/interrupted state;
- retry eligibility and bounded retry count;
- terminal refresh-proven records not being re-queued;
- unknown remaining non-negative;
- pre-existing historical cache records not being relabelled fresh;
- clean-cache and present-cache preflight behavior;
- canonical DB read-only enforcement;
- malformed/mismatched SavedVariables/session input fail-closed behavior.

Then run the complete classical project gates required by `AI_GUIDELINES.md`.

## Level-2 validation

Provide one autonomous Windows validation entry point for the remaining real-client checks after the
classical suite passes.

It should:

- reuse/configure the real WoW root without hard-coded personal paths;
- verify the exact migration-13 canonical SHA before starting;
- create/reuse a dedicated ignored campaign ledger;
- select a deterministic bounded batch automatically;
- stage/copy the minimum required in-game instruction;
- stream `[INFO]`, `[PASS]`, `[FAIL]` progress into a timestamped log;
- stop before the in-game step on preflight failure;
- require WoW to be closed for pre/post file snapshots;
- merge the real session exactly once;
- verify resume state and next-batch selection;
- reverify the canonical DB byte-for-byte at the end;
- remain open on success/failure.

For initial Level-2 acceptance, use a bounded validation campaign rather than attempting all 16,669
missing IDs. The implementation should choose a size sufficient to prove multi-ID orchestration and
resume while remaining conservative under the one-outstanding-query contract.

## Acceptance criteria

P6-T03 is `VALIDATED` only when:

- the complete Level-1 suite passes;
- the real-client campaign completes at least one automatically selected multi-ID batch;
- refresh-proven successes carry pre-miss + session success + post-WDB raw-record proof;
- unknowns remain unknown;
- duplicate session processing is idempotent;
- a subsequent run resumes from the ledger without re-querying terminal successes;
- the report quantifies success/unknown behavior and remaining candidate coverage;
- the canonical migration-13 DB remains byte-identical.

## Non-goals

P6-T03 must not:

- brute-force arbitrary item IDs;
- infer item non-existence from timeout/cache absence;
- query many IDs concurrently;
- make the validated P6-T02 timings more aggressive without evidence;
- bulk-delete or rotate WDB to refresh historical records;
- import all acquired records into the canonical DB;
- promote migration 14;
- add weapon/effect/tooltip schema;
- introduce a universal Octo/Turtle/Vanilla source order.

## Routing after P6-T03

Use measured campaign throughput and success coverage, not aspiration, to choose the next bounded step.
Likely routes include:

- a larger direct acquisition campaign if success is high and operationally practical;
- bounded migration-14 ingestion of refresh-proven records on a disposable/canonical-promotion plan;
- a separate controlled historical-cache refresh strategy if stale coverage is the dominant gap;
- field-specific OctoDB/Tortoise/Vanilla fallback investigation if direct queryability is materially
  insufficient;
- weapon damage/speed/block or item-effect semantics once acquisition coverage is adequate for those
  consumers.

Any canonical migration-14 promotion remains a separate explicit D-029 task with backup, rollback and
full-data validation.
