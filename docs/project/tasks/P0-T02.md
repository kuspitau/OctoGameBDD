# P0-T02 — Provenance and Conflict Primitives

## Objective

Implement the minimum project-owned evidence layer needed to preserve source provenance, competing
observations, and explicit canonical-selection metadata before gameplay-domain schemas are added.

This task must not turn the canonical model into a generic graph.

## Design boundary

The generic structures introduced here are **evidence/provenance storage only**.

Future canonical gameplay relations such as creature loot, quest rewards, recipe reagents, and spawn
relations must still use explicit domain tables as required by the accepted architecture.

An observation group identifies one logical fact slot for a subject. Source observations belonging to
that group may disagree without overwriting one another.

For relation-shaped evidence, the group also has a `fact_instance_key` so legitimate multi-valued
relations are not mistaken for conflicts. The default helper groups a relation by target identity, but
callers may provide an explicit stable relation-instance key when different source targets should be
treated as competing observations of the same logical relation slot.

## Implement

### 1. Version 2 migration

Add a deterministic migration after P0-T01 that creates:

- `observation_groups`;
- `source_observations`;
- `observation_import_batches`;
- `canonical_selections`;
- indexes/constraints needed for traceability, idempotency, and safe canonical selection.

Requirements:

- source observations are stable by source + source revision rather than duplicated for every rerun;
- `observation_import_batches` records every import batch that imported/confirmed an observation;
- a batch link must match the observation's source and source revision;
- scalar and relation evidence are distinguishable;
- subject kind/key and fact key remain explicit;
- relation fact instances are independently groupable;
- repeated recording of the same source evidence from the same source revision is idempotent even
  across separate import batches;
- competing values remain stored simultaneously;
- a canonical selection can only select an observation from the same observation group;
- selection policy/reason metadata is stored explicitly.

### 2. Provenance helper API

Provide small database helpers for:

- deterministic canonical JSON serialization of observation payloads;
- get/create of stable observation groups;
- recording generic observations;
- convenient scalar observation recording;
- convenient relation observation recording;
- selecting/replacing the current canonical observation for a group.

The helper layer should validate obvious malformed inputs before they reach SQLite.

### 3. Relation evidence semantics

The evidence layer must support both:

- multiple legitimate relations of the same relation type, such as one creature dropping many items;
- competing source observations for one logical relation instance, including disagreement about its
  target when a caller provides the same explicit relation-instance key.

Do not encode domain-specific cardinality or conflict-resolution policy in P0-T02.

### 4. Tests

Add/update tests for:

- fresh schema version 2 initialization;
- idempotent repeat initialization;
- upgrade of an existing version 1 database to version 2;
- deterministic observation serialization;
- source-observation idempotency within a batch and across repeated batches of the same revision;
- separation of otherwise identical observations from different source revisions;
- observation/import-batch provenance-link consistency;
- preservation of competing scalar observations;
- source/revision traceability through `import_batches` and `data_sources`;
- multi-valued relation instances;
- competing relation targets when explicitly grouped together;
- fact-kind consistency;
- confidence/authority-tier constraints;
- canonical selection and rejection of cross-group selections;
- preservation of losing observations when the canonical winner changes;
- status CLI reporting schema version 2 / two applied migrations.

## Do not implement in P0-T02

- gameplay-domain canonical tables;
- a generic canonical relation graph;
- source-specific conflict-resolution policies;
- audit/report CLI commands (P0-T03);
- pfQuest/OctoDB/Tortoise importers;
- full-data import;
- UI.
