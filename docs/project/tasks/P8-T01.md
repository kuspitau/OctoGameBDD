## Why this is the next bounded task

The project goal is an external local application for querying and exploring interconnected OctoWoW
data. The data/provenance/query layers are now mature enough for a first graphical consumer, and P7-T07
reduced representative zone-detail latency from roughly 19-38 seconds to 5-8 seconds.

A zone-centric slice is the safest first UI surface because P7-T06 already composes:

- canonical zones/maps;
- creature/gameobject spawns;
- direct/reference/vendor item acquisition;
- quest giver/finisher/objective roles;
- vendors and trainers;
- compact positive recipe-learning evidence;
- explicit unknown/truncation semantics.

This task is a UI/application task, not a new data-model or ingestion task.

## Framework-selection requirement

The architecture previously identified NiceGUI as a strong candidate, but deliberately deferred the
framework decision. That decision is now in scope and must be made from current primary evidence.

Before implementation:

1. inspect current official documentation/release status for the strongest Python-first local/browser
   candidates;
2. compare at least the needs below rather than selecting by popularity alone;
3. record the chosen framework and rationale in the appropriate architecture/decision docs if the choice
   creates a durable project dependency or architectural constraint.

Evaluate at minimum:

- local/offline-first operation;
- Python-first integration with existing query modules;
- sortable/filterable tables;
- expandable/detail-rich rows or panels;
- async/background-safe execution for multi-second read queries without freezing the UI;
- predictable local packaging/startup;
- testability;
- ability to evolve toward richer navigation/tooltips/maps without rewriting canonical/query layers.

Do not choose a frontend/API split unless current evidence shows the bounded local application needs it.

## Bounded implementation scope

Deliver a minimal but real local/browser application shell that:

1. opens the configured/canonical SQLite DB read-only;
2. exposes an obvious application start command;
3. provides a zone list/search surface using the validated P7 zone query contract;
4. supports deterministic sorting/filtering already owned by the query layer where applicable;
5. opens a zone detail view using `inspect_zone()` rather than duplicating its SQL/semantics;
6. renders at least the existing high-level sections for entities, items, quests, vendors/trainers and
   recipe evidence when present;
7. clearly represents unknown/truncated/incomplete coverage instead of hiding it;
8. shows a visible loading/progress state for multi-second zone detail reads so the UI never appears hung;
9. handles a missing/unreadable DB with a clear local error rather than creating or mutating a database.

A deliberately plain UI is acceptable. The goal is to validate architecture and interaction, not visual
polish.

## Semantic and architecture constraints

- Reuse P7 query/public conversion functions; do not create parallel SQL truth in the UI.
- Open the accepted DB read-only for normal UI exploration.
- Do not add or mutate canonical data from the UI.
- Preserve P7 three-state/unknown/truncation semantics.
- Preserve native IDs and template/spawn separation.
- Preserve independent direct/reference/vendor acquisition paths and quest roles.
- Do not persist `zone -> everything` as primary truth.
- Do not add authentication, remote hosting, multi-user support or cloud state in this task.
- Do not add dungeon/raid-specific classification, maps, saved searches, custom scoring, inventory, craft
  economics or recursive BOM analysis yet.

If the chosen framework requires a durable dependency/packaging change, document it explicitly rather
than smuggling it into an implementation file.
