# P4-T01 — spell/recipe source and identity contract

**Status: READY_FOR_IMPLEMENTATION**

## Goal

Establish the first bounded P4 contract before broad crafting ingestion: determine, from primary
sources, how OctoGameDB should identify and relate spells and recipes without conflating three
different concepts that often share user-facing names:

- the native spell learned/known by the character;
- the crafting/recipe spell that performs a craft;
- an item that teaches/unlocks that spell;
- the item produced by the craft.

The task must also establish where profession/skill-line membership and rank/skill requirements come
from, and which source surfaces are authoritative/complete versus positive/partial evidence.

P4-T01 is primarily a **source/identity-contract task**. Its purpose is to make the later recipe,
reagent and acquisition schema safe to implement.

## Preconditions

- P0 through P3-T05 are `VALIDATED`.
- The cumulative local canonical DB is `data/generated/octogamedb.sqlite3`, validated through
  migration 10 / P3-T05.
- D-029 / `docs/project/CANONICAL_DB.md` governs any future canonical DB mutation.
- Existing project rules requiring native IDs, explicit domain relations, provenance and
  recipe/spell/item distinctions remain mandatory.

No P4 task may infer that a recipe item ID, crafting spell ID and crafted item ID are interchangeable.

## Required investigation

Before designing a P4 canonical migration, inspect the relevant source behavior rather than guessing
from field names.

At minimum evaluate the useful/current surfaces that are actually available to the project, such as:

- public WoW/Vanilla DBC structures relevant to spell and skill-line identity;
- the pinned/current Tortoise source tree and world SQL where it carries recipe/trainer/item-teaching
  facts;
- CMaNGOS Vanilla schemas/data as a baseline where useful;
- pfQuest/pfQuest-turtle only for the fields they genuinely expose;
- reviewed OctoDB/Octo-specific pages only when they expose structurally meaningful P4 facts;
- the configured local OctoWoW client/addons only when public/source inspection cannot establish the
  required version-specific behavior.

Do not add a local path solely to understand a publicly inspectable format. If a real local path is
needed for Level 2 and is not already configured, follow `LOCAL_PATHS.md` and provide a safe
`get_path.bat`.

Record source revisions/versions whenever they affect parser or semantic behavior.

## Questions P4-T01 must answer

### Spell identity

- What is the stable native ID used by the relevant sources for spells?
- Which source provides a trustworthy spell name/localization for the project's default query model?
- Are ranks separate spell IDs, and if so must rank membership be modeled explicitly or deferred?
- Which source is sufficiently complete to establish spell presence versus positive-only observations?

### Recipe identity

- Is the durable recipe entity best keyed by the crafting/learned spell ID, another native ID, or an
  explicit relation over multiple native entities?
- How should the model represent a recipe that has no teaching item?
- How should the model represent multiple teaching items/sources for one crafting spell?
- Can one teaching item unlock more than one spell in any relevant source shape?
- Can a crafting spell produce multiple result items or variable quantities in the target data?

Do not choose a recipe primary key merely because a website page uses the word “recipe”.

### Profession/skill requirements

- Which source expresses profession/skill-line membership?
- Which field is the required profession skill value versus character level, spell rank or trainer
  requirement?
- Are source values complete enough to support absence/deletion semantics?
- How should profession/skill-line native identity be represented for later P4 tasks?

### Teaching/acquisition distinction

P4-T01 must explicitly distinguish:

```text
recipe/crafting spell
teaching item
trainer/NPC teaching source
quest teaching/reward source
crafted result item
```

Only the identities/relations proven in this task should be committed to subsequent P4 schema work.

## Expected deliverables

The task should produce enough durable project evidence that the next P4 implementation does not need
to rediscover basic identity semantics.

Expected tracked deliverables:

1. a P4-T01 task closeout documenting reviewed sources, revisions and exact field semantics;
2. a new architecture decision in `DECISIONS.md` if recipe identity/keying or source-priority policy
   requires one;
3. updates to `DATA_SOURCES.md` / `DATA_MODEL.md` where the established contract belongs;
4. small source-shaped fixtures and extraction/normalization code/tests when needed to prove ambiguous
   formats deterministically;
5. a bounded validation script when real/local source evidence is required.

A canonical schema migration is **not required merely to finish P4-T01**. If the investigation proves a
small identity migration is both necessary and fully bounded, the conversation may implement it only
after documenting the contract and keeping the task scope narrow; otherwise route the first schema
slice to P4-T02.

## Out of scope

Keep these out of P4-T01 unless they are inseparable from proving identity semantics:

- complete reagent ingestion;
- recipe economics/profitability;
- trainer/vendor/quest acquisition graph implementation;
- full profession progression planning;
- spell effects unrelated to crafting identity;
- combat spell modeling;
- broad item-stat ingestion;
- P6-scale full import/performance work;
- graphical UI.

## Validation expectations

### Level 1

Use reduced source-shaped fixtures to prove:

- native IDs are preserved;
- teaching item / crafting spell / crafted result are not silently collapsed;
- parsers fail closed on unsupported source shapes;
- deterministic source revisions/hashes are stable;
- any normalization retains source provenance and slot/order information where relevant.

Run all feasible pytest/Ruff/compile checks for changed code/docs tooling.

### Level 2

If the task depends on configured local Octo/Tortoise/DBC/addon data:

- resolve paths through the existing config contract;
- run exact source-version checks;
- compare representative real recipes from at least two professions or recipe families;
- include at least one recipe learned without a recipe item if such a case exists in the reviewed
  source;
- include at least one recipe item -> spell -> crafted item chain if the reviewed sources support it;
- report any source disagreement instead of forcing a universal winner.

Do not mutate the canonical migration-10 DB unless P4-T01 actually introduces a validated migration.
If it does, use a disposable copy first and then D-029 for deliberate canonical evolution.

## Completion condition

P4-T01 may be marked `VALIDATED` when the spell/recipe identity and source-completeness contract is
supported by primary/source-shaped evidence, relevant project decisions/docs are updated, and any
required local validation has passed.

The closeout must route a concrete next P4 implementation task rather than leaving “implement
crafting” as an unbounded instruction.
