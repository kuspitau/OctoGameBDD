# P2-T02 — pfQuest reference-loot resolution

## Status

`READY`

## Prerequisite

P2-T01 must be present on GitHub `main` and marked `VALIDATED` before implementation starts. The next
conversation must verify that pushed state rather than relying on this handoff package alone.

## Goal

Resolve the pfQuest item `R` reference-loot family so acquisition queries do not miss loot inherited
through reference tables, while preserving the explicit/provenance-aware model established by
P2-T01.

P2-T01 full-data validation observed `10,209` deferred `R` links, so this is a material completeness
issue rather than a theoretical edge case.

## Required investigation before coding

Inspect the primary pfQuest repository at the project-pinned/relevant revision and determine:

- the exact shape and meaning of `items[item_id]["R"]`;
- where referenced loot tables/identities are defined;
- whether references may chain or cycle;
- whether the stored value represents a probability, weight, reference ID, or another semantic;
- how pfQuest itself expands/uses these references;
- whether reference expansion combines with direct `U`/`O` chances or represents a separate
  acquisition layer.

Do not infer these semantics from the numeric shape alone. Record the inspected upstream revision and
update `DATA_SOURCES.md` if the established contract changes.

## Bounded implementation scope

After source inspection, implement the smallest correct slice that:

- preserves native IDs for any reference-loot entities;
- records reference-loot source observations/provenance;
- represents important reference relations explicitly rather than flattening away their origin;
- allows item acquisition/source queries to include correctly resolved referenced loot;
- keeps source geography derived through creature/game-object templates and P1 spawns;
- prevents duplicate acquisition rows when direct and referenced paths overlap;
- handles chained references deterministically if the source actually permits them;
- detects and safely rejects/reports cycles or malformed references if they are possible;
- remains idempotent on same-revision re-import.

The exact schema is intentionally not pre-decided here: source inspection must establish whether a
new reference-loot table/entity is required or whether an existing explicit relation model can
represent the semantics without loss.

## Explicitly deferred unless source semantics require otherwise

- vendor `V` relations (`13,860` links observed in P2-T01 validation);
- item stats/effects/requirements;
- item/container and specialized loot families;
- Turtle/Octo item overlay reconciliation;
- full P6 ingestion/performance work;
- polished UI.

If `V` proves inseparable from reference-loot expansion in authoritative pfQuest behavior, document
that dependency before widening P2-T02.

## Tests / Level 1 acceptance

Add reduced source-shaped fixtures covering at minimum:

- one item with direct loot only;
- one item whose acquisition is supplied through one reference;
- overlap between direct and referenced acquisition when applicable;
- chained reference behavior if supported;
- malformed/missing reference behavior;
- cycle behavior if references may chain;
- same-revision idempotence;
- provenance of the reference relation and resulting acquisition path;
- CLI/query output including referenced acquisition without invented geography.

Run the normal pytest/Ruff/compile checks plus focused tests.

## Level 2 acceptance

Provide an exact full-data validation command using the existing configured pfQuest path. At minimum
verify:

- the deferred `R` population is materially consumed/resolved rather than silently ignored;
- no unresolved references remain except cases explicitly reported with IDs/reasons;
- same-revision repeat import produces zero canonical inserts/updates;
- `PRAGMA foreign_key_check` is clean;
- at least one real item obtains an acquisition source through a reference-loot path;
- provenance distinguishes direct source evidence from reference-derived acquisition.

## Decision impact

No existing architecture decision is superseded by this task definition. If primary-source
inspection proves that correct reference-loot semantics conflict with the current data model, record
a new decision before changing the architecture.
