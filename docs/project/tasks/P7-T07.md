## Why this is the next bounded task

P7-T06 is semantically validated, but its accepted-canonical validation measured zone-detail latency
that is too high for the planned interactive explorer:

```text
inspect_zone(12, include_recipes=False) = 27.60 s
inspect_zone(1,  include_recipes=False) = 31.44 s
inspect_zone(14, include_recipes=False) = 41.25 s
inspect_zone(1,  include_recipes=True)  = 32.31 s
inspect_zone(3,  include_recipes=True)  = 20.85 s
```

The compact recipe correction removed the earlier pathological P7-T04 scan. The remaining cost is
therefore concentrated mainly in the P7-T05 world-entity/geography/role/provenance path that feeds
P7-T06.

The project now has representative full-data volumes, so this is the point where `TESTING.md` permits
measured performance work.

## Goal

Profile the P7-T06/P7-T05 read path on representative full data, identify the dominant costs, then
implement the smallest safe optimization that materially reduces one-zone inspection latency without
changing validated semantics or mutating the accepted canonical database.

This is a performance/query-layer task, not a new feature-domain task.

## Investigation requirements

Before optimizing, obtain measurements rather than guessing. At minimum:

1. time major `inspect_zone()` phases separately;
2. time/inspect `query_world_entities()` candidate loading, geography loading, selected `spawn_set`
   loading, filtering/sorting and retained-result role/provenance hydration;
3. inspect SQLite query plans/index usage for the dominant SQL statements;
4. compare cold/first-call and repeated-call behavior sufficiently to distinguish database I/O from
   Python/query-shape overhead;
5. record row/cardinality sizes relevant to the hot path;
6. preserve the P7-T06 accepted-canonical timings above as the pre-optimization baseline.

A small benchmark/profiling script may be added if it is deterministic, read-only and useful for human
Level 2.

## Semantic constraints

Optimization must preserve the validated P7-T05/P7-T06 contracts exactly:

- native IDs and template/spawn separation;
- independent spawn rows;
- D-026 distinct-`spawn_key` complete-set semantics and duplicate diagnostics;
- `known_match` / `known_non_match` / `unknown` behavior;
- protected/custom extra spawn handling;
- independent direct/reference/vendor paths;
- quest giver/finisher/objective separation;
- unresolved trainer evidence;
- selected provenance/role detail for returned entities;
- P7-T06 bounded/truncation and non-universal-negative semantics;
- compact positive recipe projection ownership introduced by the P7-T06 correction.

A faster result that silently drops provenance, unresolved evidence or complete-set semantics is a
regression, not an optimization.

## Preferred optimization order

Try non-persistent/read-path improvements first, guided by profiling. Examples that may be considered
when evidence supports them:

- SQL-side narrowing of known positive zone candidates before Python hydration;
- avoiding full template/spawn/provenance universe loads when the requested state/filter permits a
  provably equivalent bounded path;
- batching selected provenance/relation reads instead of repeated per-entity/per-relation lookups;
- sharing one-call indexes/caches across composed sections;
- separating cheap identity/geography candidate selection from expensive retained-result detail.

Do not preselect an implementation before profiling.

## Persistent-cache/schema guard

D-008 explicitly permits materialized derived caches only when measured performance justifies them.
This task now has measurement evidence, but it still must not silently add a persistent
`zone -> everything` truth or schema migration.

If profiling shows that a persistent derived index/cache is necessary:

1. document why non-persistent alternatives are insufficient;
2. define exactly what remains derived and how it is invalidated/rebuilt;
3. record a new/superseding decision in `DECISIONS.md` before implementation;
4. update architecture/data-model/canonical-DB docs as required;
5. use the D-029 mutation protocol for any canonical/schema evolution.

It is acceptable for P7-T07 to stop at a well-supported design decision rather than smuggle a cache
into the model.

## Full-data performance validation

Use the accepted schema-14 DB read-only. Record before/after timings on the same machine/process
protocol for at least the observed P7-T06 sample zones `1`, `12` and `14`, plus any dynamically chosen
case needed for semantic coverage.

Performance objective, not an architecture invariant:

- materially reduce the representative median one-zone latency;
- target roughly a >=3x median improvement or <=10 s representative calls on the current user
  machine if safely achievable without semantic loss;
- record exact achieved timings rather than claiming an unmeasured speedup.

If that objective cannot be met without a persistent derived structure, document the measured
bottleneck and route the explicit cache/index decision instead of weakening query semantics.
