# P6-T02 — Direct Octo item-cache freshness, coverage and bounded refresh probe

Status: `READY_FOR_IMPLEMENTATION`

## Context

P6-T01 validated the Vanilla/Octo `itemcache.wdb` record parser and a bounded provenance-preserving
item-template/stat ingestion path against the user's real Octo cache. The accepted source contract is
recorded by D-036 and `P6_ITEM_TEMPLATE_SOURCE_CONTRACT.md`.

P6-T01 deliberately stopped short of whole-cache ingestion or canonical DB promotion because a WDB
cache is observation history, not an exhaustive/current database. A present record is strong direct
Octo positive evidence, but an absent record is unknown and an old present record may be stale until
refreshed.

The final P6-T01 real-data probe selected 25 canonical item IDs and produced 25 template rows but only
3 non-empty stat-modifier rows. That result is not enough to infer global coverage quality; it is a
reason to measure coverage explicitly before expanding ingestion.

## Goal

Establish a reproducible, freshness-aware acquisition contract for direct Octo item-template evidence.

The task should answer:

> What fraction and shapes of the project's known items are actually represented in the current Octo
> item cache, how can a bounded selected item set be refreshed or queried directly without guessing,
> and what evidence is sufficient to distinguish a current observation from an arbitrary historical
> cache entry?

P6-T02 is an acquisition/coverage task. It should not widen the canonical schema merely to make more
fields writable.

## Required investigation

Inspect current primary sources before implementing a refresh mechanism. At minimum investigate where
available/relevant:

- the actual Octo client cache behavior observed locally;
- the Vanilla 1.12 item-query request/response path corresponding to `SMSG_ITEM_QUERY_SINGLE_RESPONSE`;
- current Octo-compatible client API/addon mechanisms, if any, that can request/load item information
  for a native item ID and provide an observable completion/result signal;
- relevant open-source Vanilla/Turtle/VMaNGOS/CMaNGOS client/server code only as semantic/protocol
  reference;
- existing project source-path configuration so no personal path is hard-coded.

Do not assume that deleting the whole cache, opening an item tooltip, scanning an arbitrary ID range or
waiting a fixed number of seconds is a correct refresh protocol without source/runtime evidence.

## Coverage measurements

Build a deterministic read-only report over the current real cache and the existing canonical item ID
population. At minimum measure:

- total WDB item records;
- records whose item IDs already have canonical `items` identity;
- cache-only/native IDs absent from canonical identity;
- canonical item IDs missing from the cache, reported as unknown coverage only;
- item-class/subclass and inventory-type distribution for parsed records;
- required-level/item-level distribution where useful;
- number of records with non-empty stat slots;
- number of records with armor, durability, restrictions and other already-adopted P6-T01 fields;
- representative low/high/custom native IDs when identifiable from existing project evidence;
- duplicate/malformed/unsupported record diagnostics if encountered.

The report must distinguish source coverage from canonical materialization. It must not create item
identity merely to improve the coverage percentage.

## Bounded refresh/direct-query probe

If primary-source investigation establishes a supported item-query path, implement only a bounded,
user-triggered probe first.

Requirements:

- explicit candidate item IDs; no unbounded numeric brute force;
- one/few outstanding requests according to the proven client/runtime contract rather than a tight
  flood loop;
- observable per-ID success/failure/timeout state;
- before/after raw record or normalized payload hashes so a refresh can be demonstrated rather than
  assumed;
- capture metadata sufficient to identify the client/session/realm context where practical;
- resumable behavior for a bounded list if the client/API requires asynchronous settlement;
- raw capture/cache snapshots remain ignored local artifacts;
- failure/missing response remains unknown and never negative evidence.

If no safe direct refresh/query mechanism can be established, record that result explicitly and route
a corroborating/direct source strategy instead of inventing one.

## Freshness contract target

The task must define one of these outcomes from evidence:

1. **refresh-proven direct observation** — a bounded query causes a demonstrable current response/cache
   update whose content hash can be tied to the probe;
2. **session-observed but freshness-limited** — a record can be associated with the current client
   session but not proven re-fetched from the server;
3. **historical-cache only** — current WDB bytes can be parsed but no supported refresh/currentness
   proof is available.

The final contract must state which fields/source observations may use each class and whether a later
full ingestion is allowed to select them automatically.

## Canonical DB rule

P6-T02 should not mutate or promote the canonical DB.

Current canonical baseline remains:

```text
migration 13 / 0013_recipe_acquisition_sources.sql
SHA-256 623e29d83abd20335506d2a23dcbd525331de4f1bc10d38fccd7aa550a7613d7
```

Migration 14 is validated schema capability but remains unpromoted. Use copies/snapshots for any query
or import experiments.

## Level 1 validation

Run all feasible:

- parser/report unit tests with synthetic/source-shaped caches;
- coverage classification tests;
- refresh/probe state-machine tests if a direct-query mechanism is implemented;
- deterministic hash/revision tests;
- failure/timeout/unknown semantics tests;
- full existing pytest suite;
- Ruff and compileall.

## Level 2 validation

Provide one autonomous Windows BAT for all remaining real-client/local checks after classical tests.
It should:

- reuse/discover existing source paths;
- use the real Octo cache/client data;
- preserve the canonical DB byte-for-byte;
- produce a timestamped log/report;
- stream progress for long-running operations rather than buffering the entire inner validator;
- stop clearly on critical failure;
- end with explicit success/failure markers.

If an in-game probe is required, minimize manual steps and make the exported evidence machine-readable
for the external validator.

## Non-goals

P6-T02 must not:

- treat cache absence as item absence;
- perform a whole-cache canonical import;
- promote migration 14 into the canonical DB;
- add weapon/effect/tooltip schema simply because those bytes are reachable in the packet;
- brute-force arbitrary item IDs against the live client/server;
- hard-code user-machine paths;
- introduce a universal source priority.

## Routing after P6-T02

Use measured coverage and freshness evidence to choose the next bounded P6 step. Likely routes are:

- broader/full item-template/stat ingestion under a proven freshness policy;
- weapon damage/speed/block semantics on the validated direct source;
- item effect/spell/tooltip semantics;
- a field-specific OctoDB/Tortoise/Vanilla fallback adapter where direct coverage is insufficient;
- explicit canonical migration-14 promotion under D-029 only after the intended cumulative data state
  and rollback/validation procedure are defined.
