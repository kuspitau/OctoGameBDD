# P7-T01 — provenance-aware item query/filter contract

Status: `READY_FOR_IMPLEMENTATION`

Base branch: `main`

Routing prerequisite: P6-T05 is fully integrated/committed, including the accepted migration-14
baseline SHA `60aeb4093fa68e6b3a7a8c513e5a127862d88db8bc9aab4f6f3e4a0f4c0d5a23`.

## Goal

Turn the validated P6 item-template/stat projection into the first stable P7 consumer query contract.
Provide deterministic filtering/sorting and provenance/coverage interpretation without pretending the
current real-data slice is exhaustive.

## Required scope

P7-T01 should extend the existing `octogamedb.item_search` vertical slice rather than bypass it. At
minimum, design and test a library/CLI query surface for:

- item identity/name where available;
- quality, class/subclass and inventory type;
- item level and required level;
- armor, durability and supported resistance fields;
- the existing ten-slot stat modifiers, including filtering by stat type/value;
- deterministic sort/limit behavior;
- provenance trace for selected template/stat facts;
- explicit coverage state so missing template/stat projection is not interpreted as proof that an item
  lacks that property.

Filtering semantics must distinguish:

```text
known matching fact
known non-matching fact within a materialized template
unknown / not materialized under current source coverage
```

## Constraints

- No canonical DB mutation.
- No schema migration unless a concrete query requirement proves the current migration-14 schema
  cannot express the contract; if that occurs, stop and route a separate schema task instead.
- No new global source-priority rule.
- Preserve provenance and protected-selection semantics.
- Do not fabricate fallback values for fields absent from direct Octo evidence.
- Keep public/library output deterministic and bounded.
- Existing P6 acquisition/promotion scripts are historical validation tools; P7-T01 should consume the
  accepted canonical DB rather than trigger new acquisition automatically.

## Validation expectations

Level 1 should cover representative synthetic/golden cases for filters, combined predicates, stat-slot
queries, sorting, limits, provenance and unknown-coverage behavior.

Level 2 should run read-only against the accepted local migration-14 canonical DB and demonstrate a
small representative set of real queries. It must verify that the DB SHA remains byte-identical before
and after the task validation.

## Non-goals

P7-T01 does not implement the graphical UI, saved-search persistence, weighted build scoring, full
item acquisition traversal, weapon damage/speed/block ingestion, item spell/effect ingestion, or a new
P6 acquisition tranche. Those remain later tasks driven by the stable query contract.
