## Why this task is next

The project is a multi-entity local explorer, and item exploration is a primary first-class user
capability. The validated P7 layer already exposes:

- canonical item identity and partial template/stat predicates through `query_items()`;
- explicit `known_match` / `known_non_match` / `unknown` semantics;
- deterministic sorting and bounded output;
- selected template provenance;
- direct/reference/vendor acquisition paths through `query_item_acquisitions()`;
- derived source geography without persisting arbitrary `item -> zone` truth.

P8-T01/P8-T02 established and validated the NiceGUI application/read-only interaction pattern. The
next useful vertical slice is therefore to expose the existing item contracts in the browser rather
than introduce a new domain model or ingestion task.

## Bounded goals

Add an item-search/list/detail workflow to the existing NiceGUI application while keeping P7 as the
sole owner of item/query semantics.

The first item UI slice should support the most useful already-validated filters without attempting to
expose every possible P7 option at once. At minimum consider:

- native item ID;
- name substring;
- quality;
- required-level range;
- item-level range;
- class/subclass or inventory type where presentation remains understandable;
- one or more raw stat-type minimum predicates without inventing unvalidated stat labels;
- deterministic sort/direction;
- optional display of unknown/non-match states;
- bounded result limit.

The item detail/list presentation should preserve:

- template/stat coverage state;
- predicate state rather than defaulting unknown values;
- available scalar/stat values;
- selected provenance where useful;
- acquisition paths from P7-T02, including direct/reference/vendor distinctions;
- source creature/gameobject and known zone/map geography;
- explicit unknown geography/negative-evidence limitations.

## Interaction expectations

Reuse the interaction lessons validated by P8-T02:

- Enter should submit appropriate search inputs;
- lightweight sort/state controls should have an explicit, consistent application model;
- list-to-detail navigation should be table-native and testable with stable markers;
- multi-second reads must show visible loading state and run off the NiceGUI event loop where needed;
- tests must not depend on QTable internals being exposed as ordinary visible text.

## Architecture constraints

Preserve:

```text
NiceGUI UI
  -> thin presentation/read adapter
  -> validated P7 item/acquisition query functions
  -> SQLite mode=ro + query_only=ON
```

Do not:

- add item-domain SQL to `ui_app.py`;
- create a parallel item filter implementation in the UI;
- turn unknown template/stat coverage into zero/false values;
- infer universal absence from missing acquisition/geography evidence;
- trigger P6 acquisition/promotion from browsing;
- add schema migrations or canonical DB writes;
- broaden into saved searches, weighted scores, item comparison, WoW-like tooltips/icons, crafting BOM,
  inventory ownership or economics in this first slice.

Those are separate future tasks when justified.
