# P3-T05A — establish quest quantity/reward source contract

**Status: READY_FOR_IMPLEMENTATION**

## Goal

Establish the exact reproducible source contract needed to unblock P3-T05 without inventing quest item
quantities or reward semantics.

This is a source/acquisition task, not yet the canonical P3-T05 schema implementation.

## Why this task exists

Primary-source inspection for P3-T05 established that the distributed pfQuest quest representation
loses the required quantity/reward facts:

- raw `ReqItemId*` and `ReqSourceId*` are collapsed into membership-only `obj.I`;
- the export does not preserve corresponding counts;
- guaranteed/choice item rewards are not serialized;
- public pfQuest-turtle quest data does not add those fields.

D-031 therefore blocks P3-T05 implementation until this task selects a source that actually carries
the facts.

## Source priority

Follow `docs/project/DATA_SOURCES.md` rather than inventing a new universal source order.

Investigate in this order unless evidence requires otherwise:

1. Octo-specific authoritative/maintained data, beginning with OctoDB quest records and any underlying
   stable payload/API exposed by that service;
2. direct Octo/client/server-derived evidence if a reproducible local source can carry these fields;
3. Turtle-specific/current sources if a richer maintained source exists outside the public pfQuest
   export already inspected;
4. a pinned Vanilla VMaNGOS/CMaNGOS-style baseline for facts that can legitimately be treated as
   baseline/fallback evidence;
5. other community sources only if explicitly justified.

Do not treat display text as a machine contract when a structured payload exists. Do not scrape a
source repeatedly when a deterministic cached raw artifact can be retained locally.

## Required investigation

Before adding P3-T05 canonical tables, resolve and document:

1. the exact source field/relation carrying required item ID + quantity;
2. whether required source/provided items are a distinct gameplay/source family and their exact count
   semantics;
3. the exact source representation of guaranteed item rewards and quantities;
4. the exact source representation of choice item rewards and quantities;
5. whether choice rewards have a complete set identity and whether ordering is meaningful;
6. how missing, zero, empty and absent values differ for every selected family;
7. whether duplicate/repeated item IDs can occur and how source slot/order identity is preserved;
8. coverage for Vanilla quests versus Octo/Turtle custom quests;
9. how source revisions are identified deterministically and how raw artifacts are cached;
10. how retrieval URLs/native IDs/import metadata are recorded for provenance;
11. whether the chosen source is complete enough to support stale managed-row cleanup or should be
    treated as partial observation evidence;
12. what authority/resolution policy applies if Octo-specific and Vanilla baseline sources disagree;
13. whether any non-item reward fields are structurally inseparable; otherwise leave them deferred;
14. how missing canonical item identities remain explicit unresolved evidence without placeholders.

## OctoDB investigation requirements

Because OctoDB is already listed as the project's primary Octo-specific reference, inspect it first.
Determine whether quest data is obtainable through:

- a stable structured endpoint/payload;
- embedded structured page data;
- or, only if necessary, reproducibly parseable HTML.

Record:

- representative quest URLs/native IDs;
- request/retrieval rules and polite rate limiting;
- cache format/location conventions consistent with D-014;
- deterministic revision strategy when the service exposes no immutable revision ID;
- source fields/selectors for requirements, guaranteed rewards and choice rewards;
- evidence for at least one Vanilla quest and at least one Octo/Turtle custom quest where available.

If OctoDB cannot provide a sufficiently stable or complete machine contract, document that outcome
rather than forcing an importer around brittle assumptions.

## Vanilla baseline investigation requirements

If a VMaNGOS/CMaNGOS-style source is needed, pin the exact repository/data revision and inspect the
primary `quest_template` schema/data contract for the relevant item/count/reward columns.

Treat such data as Vanilla baseline/fallback evidence unless a separate decision establishes stronger
Octo authority. Do not overwrite higher-priority Octo-specific evidence merely because the baseline
has a convenient structured schema.

## Deliverable from P3-T05A

The task should leave the repository with enough durable information that a subsequent coding
conversation can implement P3-T05 without repeating source archaeology. At minimum update:

- `docs/project/DATA_SOURCES.md` with the selected source contract, exact revisions/endpoints and
  retrieval/cache strategy;
- `docs/project/DECISIONS.md` if a new field/relation authority or reconciliation policy is adopted;
- `docs/project/tasks/P3-T05.md` to return it to `READY_FOR_IMPLEMENTATION` with the selected contract;
- `docs/project/CURRENT_STATE.md` and `docs/project/ROADMAP.md` to route back to P3-T05.

If a small parser/probe is necessary to establish the contract, add only the minimum source-shaped
fixture/probe and deterministic tests needed for that investigation. Do not prematurely implement the
full P3-T05 canonical schema.

## Validation

Where public source access is sufficient, validate the selected parser/contract with small tracked
fixtures and deterministic tests.

For a source requiring the user's local data or credentials/paths, provide exact configuration and
commands following D-021 and `docs/project/LOCAL_PATHS.md`; include `get_path.bat` in the handoff only
when a new local path is actually required.

The full tracked quality gate remains:

```text
python -m ruff check .
pytest --basetemp=.pytest_tmp
python -m compileall -q src tests scripts
```

No canonical SQLite mutation is required merely to complete source-contract investigation.

## Completion condition

P3-T05A is complete when a source contract is selected, reproducibly identifiable, documented and
validated enough to map exact required-item/source-item quantities plus guaranteed/choice item rewards
without inference.

At that point P3-T05 becomes the active implementation task again.
