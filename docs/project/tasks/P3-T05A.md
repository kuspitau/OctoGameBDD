# P3-T05A — establish quest quantity/reward source contract

**Status: VALIDATED**

## Goal

Establish the exact reproducible source contract needed to unblock P3-T05 without inventing quest item
quantities or reward semantics.

This was a source/acquisition task, not the canonical P3-T05 schema implementation.

## Why this task existed

D-031 established that distributed pfQuest quest data loses the quantity/reward facts needed by
P3-T05: `ReqItemId*` and `ReqSourceId*` become membership-only `obj.I`, corresponding counts are not
exported, and guaranteed/choice reward fields are absent. Public pfQuest-turtle quest data does not
repair that loss.

## Investigation performed on 2026-08-25

### OctoDB first

Current native-ID quest-detail pages were inspected at:

```text
https://octowow.st/db/?quest=<quest_id>
```

Representative current pages:

```text
818    A Solvent Spirit       Vanilla
815    Break a Few Eggs       Vanilla
40788  Heavy Earthen Cores    Octo/Turtle custom
40675  A Hero's Reward        Octo/Turtle custom
```

The pages expose required item/count facts and distinguish guaranteed from choice item rewards. The
custom IDs/pages demonstrate that this surface includes non-Vanilla content. No documented stable
structured quest API/payload or immutable public OctoDB revision was identified during this task.

The open Vanilla AoWoW implementation `MarkusNemesis/vanillawowdb` at revision
`06e30fae4d448eada30f465c2bef6763f9664596` was inspected only as implementation-lineage/format
corroboration. It explicitly separates ordinary item requirements, quest-start `SrcItem`, guaranteed
`RewItem` rewards and `RewChoiceItem` alternatives and carries counts in the rendered structure. It
is not treated as proof of OctoDB's exact deployed revision.

Result: OctoDB native quest pages are selected as the preferred Octo-specific **partial observation**
source for P3-T05. A future parser must cache the exact HTML, parse only recognized structural
item/count representations, use native item links/IDs, reject prose inference and fail closed on
layout/contract drift. Page absence is not negative complete-set evidence.

## Selected field contract

| Family | Meaning | Selected evidence |
| --- | --- | --- |
| `ReqItemId/ReqItemCount` | ordinary item + amount required for completion | OctoDB explicit observation first; CMaNGOS Vanilla fallback |
| `SrcItemId/SrcItemCount` | item + amount provided to the player for the quest | OctoDB when structurally exposed; CMaNGOS Vanilla fallback |
| `ReqSourceId/ReqSourceCount` | auxiliary source/drop-control item and raw source-count semantics | pinned CMaNGOS Vanilla baseline; custom Octo coverage remains unknown unless a future Octo-specific source explicitly exposes it |
| `RewItemId/RewItemCount` | guaranteed item reward | OctoDB explicit observation first; CMaNGOS Vanilla fallback |
| `RewChoiceItemId/RewChoiceItemCount` | alternative choice-reward member + amount | OctoDB explicit observation first; CMaNGOS Vanilla fallback |

D-032 records the resolution policy. Competing observations are retained. A lower-priority CMaNGOS
fact may not overwrite a selected Octo-specific observation for the same bounded fact family.

## Missing, zero, order and duplicate semantics

CMaNGOS fixed slots are complete for a present baseline quest row.

- ordinary family item ID `0` means the slot is absent;
- a nonzero ordinary-family item ID with unexpected zero quantity is preserved/reported as source
  anomaly rather than silently defaulted;
- `ReqSourceId != 0` with `ReqSourceCount = 0` is a valid explicit special case and must be retained;
- native slot number/order is provenance and is preserved before any canonical deduplication;
- repeated item IDs across slots or semantic families remain separate source observations;
- choice reward order is presentation/source slot order only, not preference/ranking.

OctoDB is partial positive evidence. Its missing sections do not mean authoritative empty sets. Counts
must come from page structure; visible prose and an omitted human-facing `1` are not quantity sources.

## Revision/cache/provenance contract

OctoDB cache location:

```text
data/raw/octodb/quests/<quest_id>.html
```

The directory is local/ignored under D-014. Retrieval should be native-ID driven, cache-first, use a
descriptive User-Agent, default to at most one request per second, use bounded transient retries and
avoid automatic parallel scraping.

Deterministic OctoDB revision:

- per page: SHA-256 of exact response bytes;
- batch: SHA-256 of a deterministic sorted `(quest_id, page_sha256)` manifest;
- source URL/native quest ID, retrieval timestamp, HTTP status/content type and content hash are
  import/provenance metadata.

The CMaNGOS baseline revision is the exact Git commit plus the named Full_DB artifact/blob above.

## Completeness/reconciliation policy

- OctoDB page evidence is partial; absence cannot trigger stale managed-row cleanup.
- A pinned CMaNGOS `quest_template` row is complete baseline evidence for its fixed slot families and
  can support bounded fallback-set reconciliation for Vanilla quests.
- Octo-only/custom quests absent from CMaNGOS simply have no Vanilla baseline observation.
- Unknown custom `ReqSource` facts remain unknown; do not synthesize them from `obj.I`, description
  text or another relation.
- missing canonical item identity remains unresolved native-ID/source/slot/count evidence without a
  fabricated item placeholder.
- non-item rewards remain deferred.
