# P6-T04 — Bounded migration-14 canonical promotion of validated item-template/stat evidence

Status: `READY_FOR_IMPLEMENTATION`

## Context

P6-T01 validated migration 14 and the bounded item-template/stat projection/import path only on a
disposable database copy. P6-T02 established D-037 freshness classes. P6-T03 validated a resumable
current-session acquisition campaign and produced real `refresh_proven_direct_observation` evidence,
while the accepted cumulative canonical DB intentionally remained migration 13.

Canonical baseline entering P6-T04:

```text
migration = 13 / 0013_recipe_acquisition_sources.sql
SHA-256 = 623e29d83abd20335506d2a23dcbd525331de4f1bc10d38fccd7aa550a7613d7
```

P6-T04 is the first task allowed to plan and execute an explicit D-029 promotion cycle for migration
14.

## Goal

Promote the validated migration-14 item-template/stat capability into the cumulative canonical DB with
a bounded, provenance-preserving source policy and a complete backup/rollback/validation protocol.

This task should establish a trustworthy canonical base for subsequent item search/filtering work; it
must not pretend that P6 direct acquisition has whole-population coverage.

## Required design work before mutation

Before writing the canonical DB, determine and document the exact eligible P6 source population for
canonical selection. The policy must explicitly distinguish at least:

```text
refresh_proven_direct_observation
session_observed_freshness_limited
historical_cache_only
unknown
```

The task must not silently collapse those classes or infer absence from cache/query failure.

If the existing D-036/D-037 decisions are sufficient, reuse them. If canonical promotion requires a
new precedence/currentness rule not already accepted, record a new decision in `DECISIONS.md` before
implementation.

## Canonical mutation protocol

P6-T04 must follow `docs/project/CANONICAL_DB.md` and D-029 exactly.

Before any canonical write:

1. verify the canonical file is migration 13 with the exact accepted SHA;
2. reject/resolve concurrent SQLite writers and sidecars as required by the canonical contract;
3. create/replace `data/generated/octogamedb_bak.sqlite3` as an exact immediate rollback copy;
4. perform migration/import/reconciliation only after the backup exists;
5. restore the backup if any required validation fails.

Do not include either SQLite file in Git or `changes.zip`.

## Bounded implementation expectations

P6-T04 should reuse the already validated migration-14 schema/importer rather than redesigning the
item model without evidence.

Required properties:

- native item IDs preserved;
- raw/source observation provenance preserved;
- existing manual/custom selections protected;
- competing observations retained;
- managed P6 selection behavior explicit and idempotent;
- no fabricated canonical identity from cache-only native IDs;
- no negative item evidence from timeout/missing;
- deterministic source revisions/evidence selection;
- repeated import/reconciliation idempotent;
- migration/FK/SQLite integrity verified;
- a bounded set of representative item-template/stat queries validated against promoted data.

## Required validation

### Level 1

Run all relevant unit/schema/import/query tests plus full repository pytest, Ruff and compileall.

### Level 2

Use the real configured P6 cache/campaign evidence and the validated cumulative canonical DB.

At minimum verify:

- exact pre-mutation migration-13 SHA;
- backup created before mutation and byte-identical to the pre-mutation canonical DB;
- migration 14 applied exactly once;
- eligible source observations imported/reconciled under the documented policy;
- rerun idempotence;
- provenance and canonical-selection expectations;
- representative item template/stat facts;
- `PRAGMA foreign_key_check` clean;
- SQLite integrity clean;
- migration-14 canonical DB only marked accepted after every required gate passes;
- rollback from `_bak` remains possible until acceptance.

Record the final accepted migration-14 canonical SHA in `CURRENT_STATE.md` and
`CANONICAL_DB.md` only after successful completion.

## Non-goals

P6-T04 does not need to:

- acquire every remaining cache-missing item;
- brute-force arbitrary native item IDs;
- solve weapon damage/speed/block if those fields remain outside the validated P6-T01 slice;
- solve item spell/effect/tooltip semantics;
- introduce a universal source priority across unrelated domains;
- build the final UI.

Those remain later bounded tasks driven by query/consumer needs.
