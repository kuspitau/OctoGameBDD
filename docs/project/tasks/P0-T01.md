# P0-T01 — SQLite Foundation and Import Metadata

## Objective

Create the minimum trustworthy SQLite/project foundation that all later importers and domain schemas will build on.

This task is intentionally narrow.

## Implement

### 1. Database location and connection

Provide a small project-owned database module that:

- opens/creates a SQLite database at a configurable path;
- enables foreign keys;
- creates parent directories when appropriate;
- has deterministic resource/transaction handling.

Do not introduce a heavy ORM unless a concrete need is demonstrated and recorded as a decision.

### 2. Versioned migration mechanism

Implement a simple versioned migration system suitable for future SQL migrations.

Requirements:

- fresh DB can be initialized;
- migrations run in a deterministic order;
- applied migration/version is recorded;
- repeat initialization is a no-op;
- migration failure does not silently mark a migration as applied.

Exact file naming/layout may be chosen by the implementation if documented.

### 3. Foundational metadata tables

Implement the minimal metadata needed before gameplay imports.

#### Schema/migration metadata

Tracks database schema version/migrations.

#### Data sources

Conceptually needs stable source identity and enough metadata for later imports, such as:

- source key;
- display name;
- source kind;
- optional URL/path;
- optional revision/build;
- timestamps as appropriate.

Do not pretend that mutable source revision belongs permanently on the source row if it is really per import run.

#### Import batches/runs

Conceptually needs:

- source;
- source revision/ref for that run;
- start/end/status;
- importer/parser version when useful;
- rows read/accepted/skipped;
- inserted/updated counts if meaningful;
- warning/error counts;
- optional structured/details field only if justified.

Keep the initial schema extensible without inventing every future field.

### 4. Minimal status CLI

Provide a command such as:

```bash
python -m octogamedb status
```

that reports at least:

- DB path;
- schema/migration state;
- registered sources count;
- import batch count.

A custom DB path should be usable through a clear CLI/config mechanism.

### 5. Tests

Add tests for:

- fresh initialization;
- repeat initialization/idempotency;
- foreign-key enforcement;
- migration recording;
- source/import-batch basic constraints;
- status command smoke behavior.

## Do not implement in P0-T01

- gameplay-domain tables;
- pfQuest/OctoDB/Tortoise importers;
- remote downloads;
- source conflict resolver;
- UI;
- full-data import.
