# P3-T05B — validate Octo live quest-query and Tortoise SQL source contract

**Status: READY_FOR_IMPLEMENTATION**

## Goal

Refine the P3-T05 source contract after the post-P3-T05A audit discovered two materially stronger
inputs:

1. direct positive quest observations obtainable from the actual Octo server/client interaction via
   ClassicAPI;
2. a current, structured Turtle 1.18.1 restoration world SQL source whose `quest_template` carries the
   quantity/reward families missing from distributed pfQuest.

P3-T05B is an acquisition/adapter/validation task. It must not add the final P3-T05 canonical schema
or mutate `data/generated/octogamedb.sqlite3`.

## Why this task exists

P3-T05A correctly resolved D-031 with the best sources known at that point: OctoDB positive
observations plus a pinned CMaNGOS Vanilla fallback. A later audit found stronger evidence that changes
the implementation strategy without invalidating P3-T05A's historical result or its field semantics.

D-033 therefore supersedes D-032 only for the **current P3-T05 source-priority/acquisition strategy**.
D-032's semantic distinctions (`ReqItem`, `SrcItem`, `ReqSource`, guaranteed reward and choice reward)
and its conservative handling of absence remain applicable unless this task establishes contrary
source evidence.

## Pinned public references from the 2026-08-25 audit

### ClassicAPI semantic reference

```text
repository: https://github.com/brues-code/ClassicAPI
revision:   e793f80f6b45ed49a94dc8abdc9fcac4fe6b03dd
branch:     master
```

Relevant code:

```text
src/quest/Data.cpp
src/quest/Details.cpp
src/quest/Cache.h
```

At that revision:

- `C_QuestLog.RequestLoadQuestByID(questID)` requests/loads quest static data and emits
  `QUEST_DATA_LOAD_RESULT` when the result settles;
- `C_QuestLog.GetQuestDetails(questID)` exposes item requirements as `{kind="item", id, count}`;
- `rewardItems` exposes guaranteed item rewards as `{id,count}`;
- `choiceItems` exposes choice rewards as `{id,count}`;
- `srcItemID` exposes the quest-start source/provided item ID;
- the exposed detail contract does **not** provide `ReqSourceId/ReqSourceCount`;
- it does not expose a source/provided-item count corresponding to `srcItemID`;
- several other server-enforced quest restrictions are absent from the 1.12 quest-query cache, so the
  API is explicitly a field-specific observation surface rather than a complete quest-template dump.

### Turtle/Tortoise world SQL reference

For P3-T05B the relevant effective source is the pinned revision's:

```text
sql/base/tw_world_quest_template.sql
sql/database_updates/world/*
```

but only the ordered world migrations that actually affect the bounded quest-template facts need to
be parsed/applied by the adapter. Do not build a general MySQL server merely to import P3-T05B.

The adapter must preserve the raw fixed-slot families and source slot number before any canonical
normalization:

```text
ReqItemId[4] / ReqItemCount[4]
ReqSourceId[4] / ReqSourceCount[4]
SrcItemId / SrcItemCount
RewItemId[4] / RewItemCount[4]
```

## Source identities

P3-T05B should introduce/reuse stable source keys conceptually equivalent to:

```text
octo-live-quest-query
tortoise-world-sql
```

Do not relabel either source as `octodb`, `pfquest-turtle`, or `octo-server-sql`.

### `octo-live-quest-query`

This is direct observation of fields returned through the user's actual Octo client/server
interaction. It is not a claim that every server-side quest-template field is visible.

A capture must retain enough environment/provenance metadata to identify the observation context,
including where obtainable:

- native quest ID;
- realm/server name;
- client/build identifier;
- ClassicAPI version/revision or an installed-file content hash;
- capture timestamp;
- success/failure status;
- exact bounded payload used by the importer;
- deterministic payload/capture hash.

A query failure or missing field is **not** global negative evidence. Only structurally present
positive fields are authoritative observations unless P3-T05B proves a stronger completeness
contract.

### `tortoise-world-sql`

This is source-shaped Turtle-lineage SQL evidence from a pinned public revision or an explicitly
identified local revision. For the pinned public source, the Git commit is part of source identity.
For a differing local checkout, hash the exact consumed base/migration inputs and record that local
content revision rather than pretending it is the pinned commit.

## Bounded field-specific priority to validate

P3-T05B should validate the following D-033 target ordering before P3-T05 implementation:

| Fact family | Preferred evidence order |
| --- | --- |
| ordinary required item + count | Octo live query -> OctoDB explicit observation -> Tortoise SQL -> CMaNGOS Vanilla |
| guaranteed item reward + count | Octo live query -> OctoDB explicit observation -> Tortoise SQL -> CMaNGOS Vanilla |
| choice item reward + count | Octo live query -> OctoDB explicit observation -> Tortoise SQL -> CMaNGOS Vanilla |
| provided/source item ID | Octo live query -> OctoDB explicit observation -> Tortoise SQL -> CMaNGOS Vanilla |
| provided/source item count | OctoDB only when structurally explicit -> Tortoise SQL -> CMaNGOS Vanilla |
| auxiliary `ReqSourceId/ReqSourceCount` | Tortoise SQL -> CMaNGOS Vanilla; current Octo-specific coverage remains unresolved |

This is a bounded P3-T05 policy, not a global ranking for other domains.

Lower-priority observations remain provenance even when a higher-priority fact is selected. A
Tortoise value selected because no Octo-specific observation exists must remain visibly
`tortoise-world-sql` evidence; it is never rewritten as confirmed live Octo truth.

## Octo live probe design requirements

Implement a small, user-triggered acquisition helper rather than a login-time full-world scan.
A minimal addon/tool may live under a project-owned `tools/` or equivalent acquisition area if that
fits the implementation discovered during the task.

The probe must:

- issue at most one outstanding quest request at a time;
- wait for `QUEST_DATA_LOAD_RESULT` before consuming the settled quest;
- call `C_QuestLog.GetQuestDetails(questID)` only after the cache/result is ready;
- persist only source-shaped bounded fields needed for this contract plus acquisition metadata;
- be resumable and deterministic enough that an interrupted capture can continue safely;
- use conservative pacing and avoid an unbounded request loop;
- start with representative IDs before any broader enumeration is approved;
- avoid retaining hundreds of full materialized detail tables in memory at once;
- fail visibly when the required ClassicAPI functions are unavailable.

Candidate IDs for later broader capture should come from the **union of known source IDs**, such as
canonical quests, current pfQuest/Turtle quest IDs, Tortoise `quest_template` IDs and explicitly
cached OctoDB IDs. Do not brute-force an arbitrary numeric range merely because the API accepts an
integer.

The raw capture remains local/ignored. A reasonable convention is:

```text
data/raw/octo-live/quest-query/<capture-id>/
```

with the original SavedVariables/raw artifact retained beside any normalized JSON projection used by
tests/importers.

## Tortoise adapter requirements

The implementation must derive an effective bounded `quest_template` view from the pinned base plus
ordered relevant world migrations.

Requirements:

- preserve source row/column/slot semantics before normalization;
- preserve `ReqSourceCount = 0` exactly;
- distinguish item ID zero (absent slot) from nonzero-ID/zero-count anomaly/special semantics;
- never deduplicate an ID merely because it appears in both `ReqItem` and `ReqSource`;
- preserve all guaranteed/choice slots and quantities;
- content-address the actual consumed source inputs in addition to recording the Git revision;
- fail closed on unsupported SQL mutation shapes affecting the bounded fields;
- use small source-shaped tracked fixtures rather than committing the full dump.

Study the Tortoise DB Viewer's staging/update parser if useful, but do not copy its derived
`quest_item` semantics into the canonical contract.

Use tracked fixtures to test at least:

- ClassicAPI-capture projection for required items/counts;
- guaranteed and choice rewards;
- `srcItemID` with no invented count;
- absence of `ReqSource` from the live capture contract;
- Tortoise base `quest_template` parsing;
- ordered bounded migration application;
- raw slot/order and duplicate preservation;
- `ReqSourceCount = 0` preservation;
- deterministic revision/capture hashing;
- fail-closed unsupported migration shape;

No P3-T05 canonical migration should be added in P3-T05B.

## Level-2/human validation

P3-T05B must provide exact commands/instructions for the user's installed Octo client and local
project. Validation should:

1. run the complete repository quality gate;
2. obtain or validate the pinned Tortoise source revision/input set;
3. run the Tortoise adapter twice and require identical source revision/output;
4. install/run the bounded ClassicAPI quest probe in the actual Octo client;
5. capture the representative Vanilla/custom quest IDs above where the server returns them;
6. import/compare the capture **without mutating the canonical DB**;
7. report per-field agreement/conflicts across live Octo, OctoDB, Tortoise and CMaNGOS;
8. confirm that missing live fields/failures are treated as unknown rather than authoritative empty
   sets;
9. determine whether broader candidate-ID capture is safe/reliable enough to support P3-T05 full-data
   validation.

If local paths are required by the implementation, that P3-T05B handoff must add the appropriate
`get_path.bat`/`LOCAL_PATHS.md` contract at that time. This documentation-only routing change does not
invent machine-specific paths in advance.

## Completion condition

P3-T05B becomes `VALIDATED` only when:

- the live ClassicAPI probe is implemented and successfully exercised on the actual Octo client;
- representative cross-source comparisons have been recorded;
- any observed limitations are incorporated into D-033/source docs;
- no canonical P3-T05 data mutation has occurred.

After that, P3-T05 returns to `READY_FOR_IMPLEMENTATION` using D-033 plus the validated P3-T05B
