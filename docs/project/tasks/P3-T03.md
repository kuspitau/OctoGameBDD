## Primary-source evidence and resolved semantics

The project-pinned pfQuest revision remains:

```text

```

The project-pinned pfQuest-turtle revision remains:


P3-T03 inspected the pinned pfQuest `toolbox/extractor.lua`, runtime `database.lua`/quest behavior,
upstream history around `close`, and the pinned Turtle `overwrites.lua`/`patchtable.lua` runtime
composition before assigning canonical meaning.

The source contract is now established:

### `lvl`

`toolbox/extractor.lua` reads `quest_template.QuestLevel` and writes `lvl` only when the value is
non-zero. pfQuest runtime presents this as **Quest Level**.

Canonical direction:

```text
quests.quest_level
```

An absent source field becomes `NULL`. A directly patched explicit numeric `0` remains `0`; it is not
silently collapsed into absence.

### `min`

The extractor reads `quest_template.MinLevel` and writes `min` only when non-zero. Runtime uses it as
**Required Level** / the player-level eligibility threshold.

Canonical direction:

```text
quests.minimum_level
```

Absent vs explicit `0` is preserved as above.

### `race`

The extractor reads `RequiredRaces` and omits a zero mask. Runtime tests the player race bit against
the mask. The pinned base runtime carries the vanilla race bit table; the pinned Turtle patch extends
race names for its custom races.

Canonical direction:

```text
quests.race_mask
```

P3-T03 keeps the raw numeric mask. It does not freeze server-specific race labels into canonical
identity-independent truth.

### `class`

The extractor reads `RequiredClasses`, omits a zero mask and runtime applies the corresponding player
class bit test.

Canonical direction:

```text
quests.class_mask
```

P3-T03 likewise keeps the raw numeric mask and its provenance rather than introducing a premature
normalized class-label table.

### `pre`

The extractor builds one deduplicated source list from:

1. `abs(PrevQuestId)` when present;
2. quests whose `NextQuestId` points to the current quest and whose `ExclusiveGroup < 0`;
3. quests whose `NextQuestInChain` points to the current quest.

The exported database does **not** retain a separate `next` field for this information.

Most importantly, pfQuest runtime checks the list with **any-of semantics**: a quest passes the
prerequisite test when at least one listed predecessor exists in completed-quest history. P3-T03 must
not reinterpret the list as all-of.

An explicit empty `pre = {}` remains distinguishable from an absent `pre` field. Lua treats the empty
table as a present prerequisite container, and runtime therefore cannot find the required
`one_complete` member. Canonical set presence is persisted explicitly.

Canonical direction:

```text
quest_prerequisite_sets(
    quest_id,
    requirement_mode = 'any_of',
    selected_set_present,
    selected_member_count
)
quest_prerequisite_set_members(quest_id, member_quest_id)
```

`follow_up` is derived by reversing selected prerequisite membership under D-008; it is not stored as
an independent primary source fact.

### `close`

Upstream history commit:

```text
ba09ad8d86a09bc53cff2b5d5c35a850813bea6a
"db: add exclusive quest groups to database"
```

and the pinned extractor establish that `close` is generated for a **positive `ExclusiveGroup`** by
listing every quest in that group. The exported member set is consequently usually symmetric across
members and commonly includes the quest itself.

No stable `ExclusiveGroup` numeric identifier survives in the exported pfQuest record. P3-T03
therefore does not invent a group identity or flatten the field into an assertion that each pair is a
generic independent "cannot coexist" edge. It preserves the complete source-provided per-quest set:

```text
quest_close_sets(
    quest_id,
    set_semantics = 'exclusive_group_member_set',
    selected_set_present,
    selected_member_count
)
quest_close_set_members(quest_id, member_quest_id)
```

Self membership in a `close` set is expected source behavior, not an error.

## Turtle composition findings

P3-T03 reuses the already validated P3-T02 compositor instead of creating a second independent
interpretation of Turtle load order.

Consequences:

- a Turtle `data-turtle[quest_id]` table replaces the base quest data entry wholesale;
- `"_"` removes the top-level quest data entry;
- an omitted P3-T03 field in a replacement row therefore becomes **absent**, not inherited;
- direct supported literal mutations in `overwrites.lua` apply before patchtable composition;
- the pinned Turtle `overwrites.lua` currently mutates an objective for quest `41682` but does not
  directly mutate `lvl/min/race/class/pre/close`;
- the exact existing P3 base/Turtle compositor revisions are reused because the P3-T03 adapter calls
  that same validated composition path rather than introducing a divergent partial loader.

## Missing-reference and source-shape behavior

A selected prerequisite/close member whose target quest identity is absent from canonical `quests`
remains source evidence and appears in:

```text
unresolved_progression_relations
```

with its native target ID. No placeholder quest/name is fabricated.

The parent set retains `selected_member_count`, while the read model also reports
`materialized_member_count` and `is_complete`. This makes missing canonical targets visible without
losing the selected source set.

Duplicate members are preserved in source-list provenance and reported in
`duplicate_source_members`; the query-oriented member set is normalized/deduplicated.

Deterministic diagnostics also report:

```text
self_prerequisite_ids
prerequisite_cycles
close_self_member_ids
close_self_missing_ids
close_group_mismatch_pairs
```

`close_self_member_ids` is informational. The other structurally odd prerequisite/close diagnostics
contribute to warnings and remain available for real-data audit instead of being silently normalized
away.

## Query/read model

`quest_by_id()` now returns a `progression` block containing:

- quest/minimum level;
- raw race/class masks;
- prerequisite set semantics, declaration flag, selected/materialized counts and named members;
- derived follow-ups;
- close-set semantics, declaration flag, selected/materialized counts and named members;
- selected source revision/policy/observation provenance for each scalar/complete set and each
  materialized primitive member.

Existing giver/finisher geography remains derived through P1 and unchanged.
