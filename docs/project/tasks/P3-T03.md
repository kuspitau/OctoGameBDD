# P3-T03 — quest restrictions and dependency graph

**Status: READY_FOR_IMPLEMENTATION**

## Goal

Extend the validated P3-T01/P3-T02 quest identity/endpoints model with the next coherent quest fact
family: player eligibility restrictions and quest-to-quest dependency structure.

Keep this task bounded. Do not combine objectives, required items and rewards into the same schema/
reconciliation change unless primary-source inspection proves that a specific field is inseparable
from the dependency/restriction model.

## Preconditions

- P3-T01 is `VALIDATED`.
- P3-T02 is `VALIDATED`.
- D-028 governs only effective quest identity + giver/finisher endpoints and must not be silently
  generalized to this new fact family.
- D-029 defines the canonical local DB lifecycle.
- The expected local cumulative baseline is:

```text
data/generated/octogamedb.sqlite3
```

validated through P3-T02.

Before any P3-T03 code or validation mutates that DB, create/replace:

```text
data/generated/octogamedb_bak.sqlite3
```

Exploratory Level-2 validation should prefer a dedicated DB copy.

## Initial primary-source evidence

The project-pinned pfQuest revision remains:

```text
shagu/pfQuest
104f35678ca39ab1fb78b655f815cc7016f5e0c8
```

Inspection of `db/quests.lua` confirms that quest entries can contain, among other fields:

```text
lvl
min
race
class
pre
close
start
end
obj
```

Examples at the pinned revision show:

- `lvl` and `min` numeric fields;
- `race` numeric masks;
- `class` numeric masks;
- `pre` arrays of quest IDs;
- `close` arrays/groups;
- these fields coexisting with the endpoint/objective families already known to P3.

Upstream history commit:

```text
ba09ad8d86a09bc53cff2b5d5c35a850813bea6a
"db: add exclusive quest groups to database"
```

explicitly introduced many `close` groups. The pfQuest extractor also names dedicated quest
predecessor/chain extraction paths (`quests_prequests`, `quests_prequestchain`).

This is enough to choose the bounded investigation, but **not enough to skip semantic verification**.
The implementation conversation must inspect the exact upstream generator/runtime behavior before
assigning canonical meanings to each field.

## Required source investigation before schema decisions

At minimum establish from primary source and the installed Turtle composition:

1. exact runtime meaning of `lvl` and `min`;
2. exact bit semantics/sentinels for `race` and `class`, including absent/default values;
3. whether `pre` means AND prerequisites, OR alternatives, chain predecessors, or another source-
   specific contract in every supported shape;
4. how `pre` is generated from server `next`/chain data and how duplicates/self-references are
   handled;
5. exact meaning of `close`, including whether it is a complete mutually-exclusive group, a
   per-quest peer set, or another closure condition;
6. whether a separate source-level `next` fact survives in the exported DB or whether follow-ups
   should be derived only as the reverse of selected prerequisite relations;
7. how Turtle top-entry replacement/deletion affects these fields;
8. whether Turtle `overwrites.lua` directly mutates any of these fields before patchtable composition;
9. which files must participate in deterministic revisions for the bounded P3-T03 source view;
10. whether explicit/custom selections require a new task-specific complete-set policy/decision.

Do not infer dependency semantics from numeric shape alone.

## Expected bounded canonical direction

Subject to the source investigation above, P3-T03 should normally add/support:

### Scalar restrictions

Potential canonical quest fields/facts:

```text
quest_level
minimum_level
race_mask
class_mask
```

Promote only source semantics that are sufficiently stable and useful. Preserve raw/source-specific
values in provenance even when a normalized canonical representation is introduced.

### Prerequisite graph

Use an explicit quest-domain relation for primitive prerequisite evidence, for example conceptually:

```text
quest -> prerequisite quest
```

Do not store `follow_up` as independent primary truth if it is merely the exact reverse of selected
prerequisite relations. In that case expose follow-ups as a derived query relation under D-008.

If source inspection establishes alternative/AND grouping semantics that cannot be represented by a
simple pairwise table without information loss, model that grouping explicitly before
materialization.

### Exclusive/closing groups

Do not flatten `close` into pairwise "cannot coexist" edges until its source semantics are confirmed.
If it represents a group identity/membership fact, prefer an explicit group/membership model or a
complete-set provenance fact that preserves the source structure.

## Provenance and Turtle reconciliation

Every supported scalar/relation must retain source revision/import-batch provenance.

P3-T02's D-028 is intentionally limited to quest identity/endpoints. P3-T03 must either:

- introduce a new bounded decision for restriction/dependency complete-view semantics; or
- explicitly justify why an existing generic primitive-selection rule is sufficient.

Do not silently copy D-028 policy names onto unrelated facts.

Turtle top-entry replacement means a patched quest may replace or remove `lvl/min/race/class/pre/close`
wholesale along with the rest of the entry. Cross-revision disappearance and stale canonical
relations therefore need explicit semantics before deletion is implemented.

## Missing-reference behavior

A prerequisite/close-group reference to a quest not currently materialized must not fabricate a quest
identity/name.

Preserve the native referenced ID in source evidence and report an explicit unresolved diagnostic
unless the source provides sufficient independent identity evidence under an established policy.

Self references, cycles and contradictory restriction/dependency shapes must be reported
deterministically; whether they are valid source data or errors depends on the source semantics
established during implementation.

## Query direction

Extend quest read/query surfaces so a caller can inspect, where supported:

- quest level / minimum level;
- race/class masks and normalized interpretation if implemented;
- selected prerequisites;
- derived follow-ups;
- exclusive-group membership/peers without losing grouping semantics;
- selected provenance for each primitive fact/relation.

Existing endpoint geography remains unchanged and derived through P1.

## Level-1 acceptance direction

Tracked source-shaped fixtures/tests should cover at least:

- `lvl` / `min` parsing and missing/default cases;
- race/class masks with documented bit semantics;
- one and multiple prerequisites;
- whatever AND/OR/group semantics primary-source inspection establishes;
- `close`/exclusive-group behavior;
- missing referenced quest IDs without fabricated identities;
- self/cycle/duplicate diagnostics as appropriate;
- preservation of explicit/custom selections;
- base vs Turtle primitive provenance;
- effective Turtle replacement/removal semantics;
- same-revision idempotence;
- migration/FK upgrade behavior if schema changes;
- query/read-model behavior.

## Level-2 acceptance direction

Against the configured real sources and the canonical local DB baseline:

1. preserve the current canonical DB under the D-029 backup rule before any direct mutation;
2. preferably validate the new importer/reconciler first on a dedicated copy;
3. record exact base/Turtle revisions and real counts for every supported restriction/dependency
   family;
4. repeat the same revisions and require zero canonical insert/update/delete changes on the second
   pass where idempotence applies;
5. run `PRAGMA foreign_key_check` and `PRAGMA integrity_check`;
6. trace at least one real multi-step prerequisite chain with provenance;
7. inspect at least one real race/class restricted quest if present;
8. inspect at least one real exclusive/close group if present;
9. confirm unresolved/cyclic/odd source cases are explicit and deterministic rather than silently
   normalized away;
10. after successful validation, evolve the canonical DB and record that it is now complete through
    P3-T03.

## Explicitly deferred

Unless source coherence forces a narrow exception:

- objective creature/gameobject/item requirements (`obj`);
- required item counts and objective text;
- guaranteed rewards;
- choice rewards;
- item-started quest acquisition semantics;
- spell/skill/profession requirements outside the bounded restriction model;
- localized quest body/objective/reward text;
- full P6 ingestion/performance work;
- UI.

## Completion condition

P3-T03 may be marked `VALIDATED` only after both Level 1 and required Level 2 checks pass and the
canonical local DB lifecycle is closed correctly. Routing should then choose the next smallest
coherent quest family from objectives/required items/rewards rather than automatically implementing
all remaining P3 fields at once.
