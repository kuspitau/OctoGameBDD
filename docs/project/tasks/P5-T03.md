# P5-T03 — Selected-vs-comparison P1 world difference audit

## Status

`READY_FOR_IMPLEMENTATION`

## Routing basis

P5-T02 validated that all `9,880` unselected single-value observation groups are intentional
`pfquest-octo` comparison evidence:

```text
expected_non_canonical_evidence = 9880
effective_view_exclusion        = 0
coverage_reconciliation_gap     = 0
policy_gap                      = 0
```

The complete unselected population comes from one successful `pfquest-octo` revision/batch. P1-T04 /
D-026 already defines that optional source as comparison evidence that is persisted without automatic
canonical selection.

Therefore P5-T03 must **not** start by changing resolution policy. The next useful question is what the
comparison source actually differs on relative to the active P1 world view.

## Goal

Add a deterministic, read-only audit surface that characterizes `pfquest-octo` P1 world differences
against the active selected/effective P1 world state.

The task should make it possible to answer, with aggregates and concrete drill-down evidence:

- which comparison-source templates/spawns are absent from the active view;
- which active subjects have comparable Octo evidence and whether the values agree or differ;
- which differences are template-level versus spawn-level;
- which fact families account for each difference class;
- which selected source/policy/effective-view evidence explains the active side where one exists;
- whether any measured subset is strong enough to justify a later, separate Octo-specific policy or
  source-coverage task.

P5-T03 measures differences. It does not promote the comparison source.

## Bounded domain scope

The primary acceptance scope is the P1 world family exposed by P5-T02:

```text
creature
creature_spawn
gameobject
gameobject_spawn
```

and the relevant facts already persisted by P1-T04, including:

```text
name
faction
level_min
level_max
world_presence
spawn_set
position
respawn_seconds
```

Only facts that actually exist for a given subject kind should be reported.

Zone/map authority remains governed by D-025 and is outside the primary P5-T03 acceptance scope unless
inspection shows a minimal zone context is required to explain a world-template/spawn difference.
Do not silently broaden P5-T03 into a new geography-authority task.

## Required comparison semantics

The report must distinguish at least these concepts without conflating them:

1. **comparison-only evidence** — a `pfquest-octo` subject/fact with no active selected counterpart;
2. **active-only evidence** — active selected/effective evidence for which the bounded comparison view
   has no corresponding subject/fact, when the available source-view semantics make that absence
   meaningful;
3. **same value** — comparison and active evidence agree under the existing canonical JSON/value
   identity for that fact;
4. **different value** — both sides provide comparable evidence and differ;
5. **not directly comparable** — complete-set/source-view semantics or subject identity do not permit
   a safe scalar equality claim.

These are audit/difference states, not canonical-selection decisions.

Where a complete-set fact such as `spawn_set` or `world_presence` explains why individual spawn facts
have no active counterpart, preserve that context in the drill-down instead of treating each spawn
attribute as an independent unexplained defect.

## Expected implementation direction

Prefer extending the existing audit layer with a generic comparison primitive rather than embedding a
one-off policy change into P1 import code.

A source-focused CLI is acceptable, for example a new audit command capable of comparing:

```text
comparison source = pfquest-octo
active side       = selected/effective canonical evidence
```

The exact CLI spelling should follow existing project conventions after inspecting `__main__.py` and
`audit.py`.

The implementation may use persisted provenance/canonical selections when sufficient. If complete
source-view membership cannot be reconstructed safely from SQLite alone, it may reuse the validated
P1-T03/P1-T04 effective-view loaders and existing configured source paths. In that case:

- read `docs/project/LOCAL_PATHS.md` before designing path handling;
- reuse existing `[source_paths]` keys rather than inventing new machine-specific paths;
- do not hard-code user paths;
- record the exact compared source revisions.

## Required aggregates and drill-down

At minimum, deterministic JSON should provide:

- total compared subjects/groups/observations;
- counts by subject kind;
- counts by fact family;
- counts by comparison state;
- source revision/import-batch provenance;
- selected source/policy aggregates for the active side when applicable;
- correlated template/spawn pattern summaries;
- bounded detailed examples with both sides' evidence and sibling/complete-set context.

A summary-only mode analogous to P5-T02 `--limit 0` is preferred for full-data validation if detailed
rows would be large.

Filters should be sufficient to isolate at least:

- subject kind;
- subject key where meaningful;
- fact key;
- comparison/difference state.

## Explicitly out of scope

- no migration;
- no canonical DB mutation;
- no automatic canonical selection;
- no global source-priority change;
- no promotion of `pfquest-octo` merely because it contains unique data;
- no silent change to D-026;
- no P2/P3/P4 source comparison expansion;
- no full P6 source scaling;
- no UI work.

If evidence later justifies treating some Octo-specific fact family as authoritative, that must be a
separate task with an explicit architecture/decision update.

## Level-1 acceptance

Use small provenance/effective-view fixtures to cover at least:

- one comparison-only subject/fact;
- one active-only subject/fact where absence is semantically meaningful;
- one same-value comparison;
- one differing-value comparison;
- one complete-set/spawn case where parent `spawn_set` context explains child spawn differences;
- selected source/policy context on the active side;
- deterministic aggregate ordering/JSON output;
- filters and bounded drill-down;
- read-only byte-hash behavior on the fixture DB.

Existing `source`, `trace`, `conflict`, `coverage`, `resolution`, and `unselected` behavior must continue
to pass.

## Level-2/full-data acceptance

Run against an isolated snapshot/copy of:

```text
data/generated/octogamedb.sqlite3
```

with expected canonical baseline SHA-256:

```text

```

The P5-T02 comparison-evidence baseline to account for is:

```text
creature groups                         = 9

gameobject groups                       = 11

```

with source revision:

```text
sha256:eddd325a9a0eab2616c7b70d03e23d55f1a0c4127a293426ea07a17c0f2421db
```

Acceptance should:

1. preserve the P5-T01/P5-T02 resolution counts;
2. account deterministically for the measured `pfquest-octo` comparison evidence in the new
   difference report;
3. expose aggregate difference states and bounded real examples for all four primary subject kinds;
4. preserve enough complete-set/sibling context to explain spawn-level differences without guessing;
5. record compared source revisions/batches;
6. prove the validation snapshot and canonical DB SHA-256 remain unchanged.

Do not define an expected count for `same`, `different`, `comparison-only`, or `active-only` before the
real report measures them.

## Closeout decision

P5-T03 closeout must summarize the measured difference classes and decide the next bounded action from
evidence.

Possible outcomes include:

- all meaningful Octo differences remain informational/comparison-only -> proceed to domain-specific
  coverage/completeness auditing;
- a clearly bounded Octo-specific fact family has stronger authority/completeness evidence -> create a
  separate source/selection-policy task and update `DECISIONS.md` explicitly;
- a loader/reconciliation defect is discovered -> route a bounded corrective task before further P5
  auditing.

P5-T03 itself must not make those policy changes silently.
