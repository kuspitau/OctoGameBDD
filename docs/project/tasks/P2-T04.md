# P2-T04 — pfQuest-turtle effective item/acquisition reconciliation

## Status

`READY`

## Prerequisite

P2-T03 must be present on GitHub `main` and marked `VALIDATED` before implementation starts.

## Goal

Reconcile the already-supported P2 item/acquisition facts with the user's active
`pfQuest + pfQuest-turtle` effective item view, so custom/replaced/removed Turtle item entries do not
remain silently represented by stale base-pfQuest canonical relations.

This is a bounded correctness task. It does **not** add broad item stats/effects/requirements or new
loot families.

## Why this is next

P2-T01 through P2-T03 validated the base-pfQuest item slice for:

- item identity/name;
- direct creature/game-object acquisition (`U` / `O`);
- one-level reference loot (`R`);
- vendor acquisition (`V`).

The active local environment also contains `pfQuest-turtle`. Prior source review established that the
Turtle addon includes item patch data and applies top-entry replacement semantics. The current P2
importer still consumes the base item view, so a changed or removed Turtle item entry can leave stale
base acquisition truth in the canonical database.

Correct the effective view before widening P2 into richer item fields.

## Required primary-source investigation

Before designing reconciliation, inspect the relevant current/pinned Turtle primary source and the
user's supported local source shape as needed to establish:

- exact item/localization files loaded by `pfQuest-turtle`;
- load order relative to base pfQuest item/localization data;
- whether `items-turtle` entries are whole-entry replacements, deletions, or have any special
  overwrite behavior;
- how item names/localization are patched;
- whether vendor/reference/direct-loot targets introduced by Turtle require Turtle unit/object
  identity inputs beyond the already materialized P1 world;
- whether any `overwrites.lua` behavior mutates the bounded item/acquisition tables outside the
  literal patch tables;
- whether the installed local addon differs materially from the reviewed public revision.

Do not infer effective item semantics merely from the P1 world overlay implementation.

## Architecture checkpoint

D-026 is explicitly bounded to the P1 world effective-view problem. Do **not** silently generalize it
to items.

If correct item reconciliation requires durable representation of effective-source item presence,
complete relation sets, or canonical deletion/replacement semantics, determine whether:

1. the existing generic provenance primitives already represent the needed facts without changing
   accepted semantics; or
2. a new decision must be recorded in `docs/project/DECISIONS.md` to extend/generalize the policy.

Any new decision must also update the affected data-model/source documentation.

## Bounded implementation target

The smallest acceptable slice should reconcile only facts already supported by P2-T03:

- item identity/name when the effective source supplies it;
- direct `U` creature acquisition;
- direct `O` game-object acquisition;
- one-level `R` reference-loot acquisition;
- `V` vendor acquisition and exact source `maxcount` evidence.

Required behavior:

- preserve native item/reference/creature/game-object IDs;
- preserve base and Turtle source evidence separately;
- apply the actual effective source replacement/deletion semantics rather than merge-by-accident;
- remove or supersede stale canonical P2 relations only under an explicit provenance-aware policy;
- retain unrelated/non-pfQuest selected evidence;
- preserve P2-T01/T02/T03 meanings for direct loot, reference loot and vendors;
- reuse P1 canonical templates/spawns/geography rather than inventing item geography;
- remain same-revision idempotent;
- report unsupported/ambiguous overlay mutations explicitly rather than guessing.

## Level-1 acceptance

Use reduced source-shaped fixtures covering at minimum:

- unchanged base item through the effective view;
- Turtle-added item;
- Turtle whole-entry replacement changing one or more of `U`/`O`/`R`/`V`;
- Turtle removal of an item entry if the source supports deletion;
- stale canonical relation cleanup/replacement under the selected provenance policy;
- base and Turtle evidence retained separately;
- protection of explicit/non-pfQuest canonical selections;
- relation-only source identity where applicable;
- same-revision repeat reconciliation with zero canonical changes;
- query behavior after addition/replacement/removal;
- migration compatibility if a schema change is genuinely required.

## Level-2 acceptance

Against the configured full pfQuest/Turtle inputs:

1. rebuild a fresh bounded P1 world and active Turtle world reconciliation;
2. import/reconcile the P2 effective item/acquisition view;
3. report base-vs-effective counts for items and each supported relation family;
4. require same-revision second reconciliation to produce zero canonical changes;
5. run `PRAGMA foreign_key_check`;
6. identify at least one real Turtle-added/changed/removed item or acquisition relation and show the
   resulting canonical/query behavior;
7. trace both base and Turtle provenance for that example;
8. confirm previously validated direct/reference/vendor semantics remain intact for unaffected data.

Prefer a fresh bounded dependency chain over an arbitrary cached generated database.

## Explicitly deferred

- richer item stats/effects/requirements;
- item/container and specialized loot families;
- generalized economics/AH data;
- broad `pfQuest-octo` item reconciliation unless required to understand a conflict;
- full P6 ingestion/performance work;
- UI.
